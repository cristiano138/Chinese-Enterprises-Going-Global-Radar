## 1. 文档目的

本文说明数据库中每张表、每个字段的含义和用途，并记录 2026-10-18 的乱码治理：

1. 哪些“乱码”是真正的字符损坏，已经修复；
2. 哪些“乱码”其实是二进制存储，不应修改；
3. 哪些问题来自官方源文件本身，只能标注、不能臆造；
4. 修复的方法、范围、校验结果和回滚方式。

## 3. 乱码治理记录（2026-10-18）

### 3.1 问题分类

| 现象 | 位置 | 性质 | 处理 |
|---|---|---|---|
| `Ð` 出现在英文正文中，如 `PART 15ÐRADIO FREQUENCY`、`TABLE 1ÐContinued`、行首 `ÐComputers` | `documents.full_text`、`units.body` | PDF 字体映射错误：破折号 `—`／连接号 `–`／项目符号 `•` 被错误映射为 `Ð` | 已用库内原始 PDF 重新抽取对齐后修复 |
| `±` 被当作连字符／范围号，如 `CAS Reg. No. 164907±73±7`、`2390±2400 MHz`、`FR Doc. 95±5625`、`U±NII` | 325 篇老版 Federal Register／年度 CFR 文档 | 同一类 PDF 字体映射问题；但 `±` 也可能本来就是合法容差符号 | 用原始 PDF 校正；无法确认的保留原样并在报告中列出 |
| 希腊文整段错乱，如 `GR AAÐÁÍÙ ÌAAÑÏÓ` | `EU-DOC:31994L0011` 的 2 个条款、`documents.full_text` | EUR-Lex 提供的原始 HTML 本身已损坏，不是采集或存储造成的 | 保留原样；见 3.4 |
| `blobs.payload`、`documents_fts_data.block`、`documents_fts_docsize.sz` 显示为乱码 | 二进制列 | 这些列本来就是 BLOB（压缩文件字节／FTS5 内部结构），不是文本 | 不修改；见 3.5 |
| `T EST`、`M AXIMUM`、`R ADIO` 等大写字母间多空格 | PDF 抽取文本 | 版面／字体抽取伪影，不是字符编码问题 | 未自动修改；法律复核应回看原 PDF |

### 3.2 修复方法

1. **以原始文件为准**：从 `blobs` 解压该文档的 `official_pdf`，用 PyMuPDF 重新抽取文本。
2. **逐字对齐**：把旧正文和新抽取文本都去掉空白，得到连续字符序列；对每个 `Ð`／`±`，用前后各 8—100 个非空白字符作为上下文，在新文本中定位对应字符。
3. **只接受可信替换**：替换字符必须属于破折号、连接号、项目符号、合法 `±` 或小数点等合理集合；字母、数字等可疑结果一律拒绝。
4. **保守回退**：无法定位时，`Ð` 按行首项目符号／破折号规则处理；`±` 仅在明显标识符（FR Doc、Docket、CAS 号、电话、频段、法条编号等）中改为 `-`，其余保留。
5. **同步 `units.body`**：受影响文档的 `units.body` 经核验 100% 是 `documents.full_text` 的精确子串，因此直接取修复后 `full_text` 的对应切片，保证正文与条款一致。
6. **重建 FTS**：对每个正文发生变化的文档，在 `documents_fts` 中删除并重新插入该行，使索引与 `documents.full_text` 一致。
7. **原始字节未动**：`blobs` 中的 PDF、XML、JSON 等原始文件字节完全未修改，随时可回溯。

### 3.4 未修复／需人工注意的事项

1. **`EU-DOC:31994L0011` 的希腊文**：库内原始 HTML 中该表本身就是 `GR AAÐÁÍÙ ÌAAÑÏÓ` 等错乱字符，无法从库内资料恢复。涉及该表格时应回看 EUR-Lex 官方页面或纸质原件，不应按现有文本推断希腊文名称。
2. **保留的 `±`**：部分 `±` 无法判断是连字符、小数点还是真实容差（例如 `37±8 °C`、`1.33±0.02 grams`）。为避免把合法容差改成错误符号，这类字符保留原样。详细信息见 `maintainer/pdf_repair_report.txt`。
3. **PDF 版面伪影**：大写标题中的多余空格（`T EST`、`M AXIMUM`）、断词连字符、表格列顺序等，属于 PDF 抽取的版面问题，不影响“字符编码”层面，但会影响可读性和机器解析。法律复核请以原始 PDF 为准。
4. **合并文本、eCFR、FR XML 的法律效力**：见第 7 节。
5. **历史引证缺口**：`source_citations.match_status` 为 `unresolved`／`ambiguous` 的记录仍存在，属于既定的历史出处缺口。

### 3.5 关于 BLOB“乱码”

用户在 SQLite 图形工具中最右侧看到的“乱码”，多数是二进制列。它们不是文本损坏：

| 列 | 存储内容 | 正确读取方式 |
|---|---|---|
| `blobs.payload` | 原始文件字节（`encoding='zlib'` 时为 zlib 压缩流，`identity` 时为原样字节） | `zlib.decompress(payload)`（仅 zlib）；`sha256` 是解压后字节的 SHA-256，`raw_size` 是解压后大小 |
| `documents_fts_data.block` | FTS5 倒排索引的二进制段数据 | 不要直接读；通过 `documents_fts` 查询 |
| `documents_fts_docsize.sz` | 每行 token 数的变长二进制编码 | 不要直接读；由 FTS5 内部使用 |
| `documents_fts_idx.term/pgno` | FTS5 词项索引 | 通过 `documents_fts` 查询 |

`blobs` 当前共 3,197 条：`identity` 272 条、`zlib` 2,925 条；解压后总计约 1.69 GB，压缩存储约 786 MB。抽样 20 条验证：`sha256(解压后字节) = blobs.sha256`，且 `length(解压后字节) = raw_size`。

#### 4.1.1 `seed_json` 的 20 个字段

顺序由 `settings.seed_field_order` 固定：

`类目`、`机构`、`监管机构`、`法规中文名`、`官方标题（英文）`、`官方编号`、`CELEX号`、`ELI标识`、`官方链接`、`来源类型`、`现行效力`、`生效日期`、`最新修订日期`、`链接可打开`、`编号核对`、`是否官方来源`、`核对状态`、`核对人`、`核对日期`、`备注／问题`。

这些是人工底表字段，采集程序不做“纠正”；其中 `核对状态`、`核对人` 等是业务核对记录，不等于本库的自动校验结果。

## 7. 阅读与使用注意事项

1. **不是法律意见**：本库是资料存档。`full_text`／`units.body` 是抽取文本，`units` 未经逐项法律校核；正式法律判断应回看原始 PDF 或官方页面。
2. **区分版本性质**：
   - 欧盟合并文本（`eu_consolidated`）无独立法律效力；
   - 美国 eCFR（`us_ecfr`）是非正式法律版本／检索副本；
   - 年度 CFR（`us_annual`）是年度编纂版本，不是最初颁布原件；
   - 正式发布 PDF 单独标注为官方发布文件。
3. **日期不要混用**：`events` 中同名的日期属性可能表示不同法律语义。不要把下载日、快照日、编纂日、合并日当成生效日；`version_date` 也不是生效日。
4. **元数据批次问题**：`document_metadata.scoped_json` 已按文档筛选；不要用整批原始响应直接证明单条法规。
5. **`seed_json` 是人工底表**：其中 `核对状态`、`核对人` 等是业务记录，不代表本库自动核验通过；`association_review` 仍有 2 条“待复核”。
6. **二进制列不要当文本读**：`blobs.payload`、FTS5 的 `block`／`sz` 是二进制；GUI 中的“乱码”是正常显示，不是数据损坏。
