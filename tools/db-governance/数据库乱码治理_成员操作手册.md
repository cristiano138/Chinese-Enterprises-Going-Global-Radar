# 数据库乱码治理：成员操作手册

- 手册版本：2026-10-18
- 适用数据库：`regulations.sqlite3`（2026-10-17 交付版）
- 补丁文件：`governance_patch.json.gz`
- 应用脚本：`apply_db_governance.py`
- 补丁 SHA256：`cd5374f37cf5f49b30389bccfc5a76cbfe72048538b9f57bab3731a4cabfab8a`
- 补丁大小：78,624 字节（解压后约 267 KB）
- 补丁内容：325 篇文档、15,249 处单字符修正
- 分发压缩包：`治理补丁包_成员版_20261018.zip`（内含 `apply_db_governance.py`、`governance_patch.json.gz`、本手册；压缩包的 SHA256 见同目录 `治理补丁包_SHA256.txt`）

> 这份手册给“手里已经有一份数据库”的成员使用。按下面步骤操作，脚本会自动备份、自动校验，只修改该改的文本，不会动原始文件字节，也不会改表结构。

---

## 0. 一分钟版

1. 关闭所有正在打开数据库的软件（DB Browser、DBeaver、Navicat、VS Code 的 SQLite 插件等）。
2. 确认电脑有约 **3 GB 可用空间**（脚本会自动备份）。
3. 把 `apply_db_governance.py`、`governance_patch.json.gz` 和你的 `regulations.sqlite3` 放在同一个文件夹（或记住数据库的完整路径）。
4. 打开命令行，运行：

```bash
python apply_db_governance.py --db "你的路径/regulations.sqlite3"
```

5. 等待 3—5 分钟。看到最后一行 **`结果：成功`** 即完成。
6. 自动备份文件为 `regulations.sqlite3.bak-governance-<时间戳>`，至少保留到确认数据无误。

如果只想先看看会发生什么，不写数据：

```bash
python apply_db_governance.py --db "你的路径/regulations.sqlite3" --dry-run
```

## 1. 这次治理到底改了什么

只修改三处：

| 对象 | 修改内容 |
|---|---|
| `documents.full_text` | 325 篇英文正文中的字体映射乱码（`Ð`、被误用的 `±`） |
| `units.body` | 上述文档对应的条款／段落切片，共 1,179 行 |
| `documents_fts` | 上述文档的全文索引，共 325 行 |

**不修改**：

- `blobs` 中的原始 PDF／XML／JSON 字节；
- `laws`、`documents` 的其他字段、`artifacts`、`responses`、`events`、`relations` 等；
- 表结构、字段、索引；
- 任何法规标题、编号、日期、状态。

因此，治理只影响“可读文本”和“全文检索”，不影响出处、版本和原始档案。

## 2. 适用前提

### 2.1 你的数据库应该是哪一版

补丁针对 2026-10-17 交付的原始库。原始文件的 SHA256 应为：

```text
bfb145a5c8ccf6a65809ddc237bdf0e463efc4e03e1b6e52dee64c0f9150012b
```

团队完成治理后的库，SHA256 为：

```text
8324386b657d3a897e96c8b0efac397224bb193dc3646122b4db0653d50948c6
```

但**不需要**先匹配整库 SHA。真正决定能否应用的是每篇文档的正文哈希：

- 脚本会逐篇比较 `documents.full_text` 的 SHA256；
- 与“治理前”一致 → 应用该篇；
- 与“治理后”一致 → 跳过（已经修过）；
- 两者都不一致 → **跳过并报告**，绝不强行修改。

所以即使你的库被手动改过，脚本也只会处理它确认安全的部分，并列出不匹配的文档。

### 2.2 检查整库 SHA（可选）

Windows PowerShell：

```powershell
Get-FileHash .\regulations.sqlite3 -Algorithm SHA256
```

macOS / Linux：

```bash
shasum -a 256 regulations.sqlite3
```

如果整库 SHA 是 `bfb145...`，说明是原始交付版，可以直接按本手册操作。

## 3. 准备工作

### 3.1 安装 Python（只需一次）

要求 Python 3.8 或更高版本。应用脚本**只用标准库**，不需要 `pip install` 任何东西。

检查：

```bash
python --version
```

Windows 上如果 `python` 不可用，可尝试：

```bash
py -3 --version
```

后续命令中的 `python` 相应替换成 `py -3`。

### 3.2 关闭数据库

在做任何操作前，关闭所有可能占用数据库的软件：

- DB Browser for SQLite、DBeaver、Navicat、DataGrip、SQLiteStudio；
- VS Code / PyCharm 中打开的 SQLite 连接；
- 任何正在跑采集、分析或导出脚本的 Python 进程；
- OneDrive／坚果云／百度网盘等同步工具（建议暂停同步，避免文件被锁）。

如果目录中存在 `regulations.sqlite3-wal` 或 `regulations.sqlite3-shm`，通常没问题；只要没有其他程序正在写入即可。

### 3.3 准备文件

建议新建一个文件夹，例如 `D:\db-governance\`，放入：

```text
apply_db_governance.py
governance_patch.json.gz
regulations.sqlite3          （或使用它原来的完整路径）
```

不要把数据库放在只读目录、压缩包内或网络共享盘的只读位置。

### 3.4 磁盘空间

脚本会在写入前自动创建一份完整备份，大小约 2.1 GB。请确保数据库所在磁盘至少有 3 GB 可用空间。

## 5. 应用后怎么抽查

用你平时使用的 SQLite 工具打开数据库，执行：

```sql
-- 1. 应该只剩欧盟那篇源文件损坏的文档
SELECT id, length(full_text) - length(replace(full_text, 'Ð', '')) AS eth_count
FROM documents
WHERE full_text LIKE '%Ð%';

-- 2. 全文索引与正文应该完全一致
SELECT COUNT(*) AS mismatch
FROM documents_fts f
JOIN documents d ON d.id = f.document_id
WHERE f.body IS NOT d.full_text;

-- 3. 抽查被修复的句子
SELECT substr(full_text, instr(full_text, 'PART 15') - 40, 200)
FROM documents WHERE id = 'US-FR:96-14138';

SELECT substr(full_text, instr(full_text, '5.15') - 60, 160)
FROM documents WHERE id = 'US-FR:97-2007';
```

预期：

- 第 1 条只返回 `EU-DOC:31994L0011`，计数为 2；
- 第 2 条返回 0；
- 第 3 条能看到 `PART 15—RADIO FREQUENCY`、`5.15–5.35 GHz`。

也可以直接全文检索：

```sql
SELECT document_id, title
FROM documents_fts
WHERE documents_fts MATCH 'radio AND frequency'
LIMIT 10;
```

## 6. 回滚

如果需要恢复到治理前：

1. 关闭所有数据库工具；
2. 删除或移走当前的 `regulations.sqlite3`、`regulations.sqlite3-wal`、`regulations.sqlite3-shm`；
3. 把 `regulations.sqlite3.bak-governance-<时间戳>` 改名为 `regulations.sqlite3`；
4. 重新打开数据库。

如果你在运行前自己做过备份，也可以用你自己的备份。

回滚后，文本乱码会重新出现，但原始文件、元数据和表结构一直未受影响。

## 7. 常见问题

### 7.1 `database is locked`

原因：还有程序占用数据库。

处理：

1. 关闭所有 SQLite 工具和 Python 进程；
2. 暂停 OneDrive／网盘同步；
3. 等待 10 秒后重试；
4. 仍不行时，把数据库复制到一个本地普通文件夹（如 `D:\db-governance\`）再运行。

### 7.2 `mismatch` 大于 0

说明有些文档的正文哈希既不是“治理前”，也不是“治理后”。常见原因：

- 你的库不是 2026-10-17 交付版；
- 有人已经手动改过这些正文；
- 数据库来自另一条采集批次。

处理：

- **不要**尝试强行修改；
- 把脚本输出中列出的文档 ID 和哈希发给维护人；
- 脚本已经跳过了这些文档，其余匹配的文档仍会正常修复。

### 7.3 提示 `No module named ...`

应用脚本只用标准库。如果出现缺模块，通常是你运行了别的脚本，或 Python 环境不完整。先确认：

```bash
python --version
```

应为 3.8+。若仍报错，把完整报错发给维护人。

### 7.4 `Permission denied` / `拒绝访问`

- 数据库可能在只读目录或受保护目录；
- 复制到 `D:\db-governance\` 这类普通可写目录再运行；
- 不要放在压缩包里直接运行。

### 7.5 备份失败或空间不足

脚本在写入前会创建约 2.1 GB 的备份。请至少预留 3 GB。若空间不足，可先清理磁盘，或手动把数据库复制到空间充足的磁盘再操作。

### 7.6 运行很慢

首次应用需要逐篇重写正文、条款和 FTS，约 3—5 分钟；机械硬盘或同步盘可能更慢。第二次运行会非常快（只做哈希校验）。

### 7.7 控制台中文显示为乱码

只是终端显示编码问题，不影响数据库内容。可以改用 PowerShell 或设置 UTF-8：

```powershell
chcp 65001
```

### 7.8 `eth_docs` 里出现欧盟文档之外的结果

说明你的库中存在补丁未覆盖的额外 `Ð`。不要手动替换；把结果发给维护人，确认是否需要扩展补丁。

### 7.9 `fts_body_mismatch` 不为 0

先重新运行一次应用脚本（它会重建已应用文档的 FTS）。若仍不为 0，把输出发给维护人。

## 8. 补丁的技术说明（给需要审计的成员）

- 补丁是 gzip 压缩的 JSON，不是 SQL 脚本；
- 每篇文档记录：
  - `id`：文档 ID；
  - `length`：正文长度；
  - `old_sha256`：治理前正文哈希；
  - `new_sha256`：治理后正文哈希；
  - `edits`：`[字符位置, 新字符]` 列表；
- 所有修正都是**等长单字符替换**，因此位置可以直接应用；
- 补丁生成方法：用 `blobs` 中的原始 PDF 重新抽取文本，与旧正文去空白对齐，逐字确定应替换的字符；详见 `数据库字段说明与治理记录.md`；
- 补丁不包含任何原始文件字节，也不包含整篇正文，体积很小；
- 应用脚本只使用 Python 标准库（`sqlite3`、`gzip`、`json`、`hashlib`），不联网。

如果你需要独立复核，可以让维护人提供：
- `make_governance_patch.py`：补丁生成脚本；
- `repair_with_pdf.py`：基于原始 PDF 的完整重抽取脚本；
- `pdf_repair_report.txt`：逐文档统计和未决样本。
