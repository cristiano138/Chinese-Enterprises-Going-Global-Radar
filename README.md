## 这个项目解决什么问题

### 场景

一个卖家要把商品卖到海外市场，必须先搞清楚：**我这个品类，目标市场有哪些法规要求？最近有没有变化？我现在要做什么准备？**

### 现状有多难

| 痛点 | 具体表现 |
|---|---|
| **法规分散** | 各国官网各查一遍，欧盟要查 EUR-Lex，美国要分别查 FDA / FCC / CPSC / FTC |
| **语言与专业门槛** | 全是英文法律术语，非专业背景根本读不懂 |
| **更新跟不动** | 法规频繁修订甚至整部被取代，卖家往往事后才知道 |
| **通用 AI 不可靠** | 直接问大模型容易编造条款号、引用已被废止的旧法规，且不给来源 |

### 两种需要核实的风险

**法规生效与一般适用日期不同**

欧盟新玩具法规处于过渡安排中：

- **Regulation (EU) 2025/2509** 于 2025-11-26 通过，**2026-01-01 生效**
- 一般自 **2030-08-01 适用**；部分条文自2026-01-01提前适用，旧 **Directive 2009/48/EC** 的废止及产品过渡另有安排

不能因为新法规已生效，就把旧指令整体提前判为无效。具体产品仍须按适用日期、过渡条件和实际投放时间核验。[新法规官方原文第56、57、59条](https://eur-lex.europa.eu/eli/reg/2025/2509/oj/eng)。

**法规编号和模型回答需要证据**

模型回答中的法规编号必须回到官方来源核实。当前仓库没有可以公开核验的真实模型对照回放，不能据此宣布某个编号不存在，也不能预写本工具与通用模型的胜负。

模型对照模块如实显示“尚未生成对照记录”；目录查询、链接可访问和机器读取都不代表具体产品已经通过合规审核。

**这正是本工具的切入点：不靠 AI「记得」法规，而是让它「查」到法规 —— 且每条结论都能点开官方原文核实。**

## 为什么是这些品类与市场

### 品类不是随手选的 —— 是监管数据标出来的

数据来源：欧盟委员会《2024 Safety Gate 年度报告》（2025-04 官方发布）。2024 年全欧危险产品警示 **4137 次**，创 2003 年系统建站以来最高纪录。被警示最多的品类：

| 警示品类 | 占比 | 本项目是否覆盖 |
|---|---|---|
| 化妆品 | **36%** | ✅ 美妆个护 |
| 玩具 | **15%** | ✅ 儿童玩具 |
| 电器 | **10%** | ✅ 电子电器 |
| 机动车 | 9% | — |
| 化学品 | 6% | — |

**召回榜前三名，正是本项目覆盖的三个品类。** 这不是我们先定品类再找依据，而是监管机构的真实召回数据告诉我们：这些品类最容易出事、最需要有人帮卖家看清规则。

### 目标用户同样是官方数据里被点名的

同一份报告：

| 数据 | 数值 |
|---|---|
| 警示产品最大来源地 | **中国，占 40%** |
| 扣除化妆品后 | **中国占 61%**（第二名欧洲经济区仅 19%） |
| 2024 年欧盟进口低价商品 | 46 亿件，日均 1200 万个包裹，**其中 91% 来自中国** |

> 欧盟每 10 件被查出的危险产品，有 4 件（扣掉化妆品是 6 件）来自中国。**中国卖家正是最需要提前搞清法规的人群 —— 我们的目标用户，是被官方数据点名的。**

### 市场选择有出口数据支撑

数据来源：中国海关总署（2025 年数据）、安永《2025 消费品出海白皮书》。

| 出口目的地 | 占比 |
|---|---|
| **美国** | **34.2%（第一）** |
| 英国 | 8.1% |
| 德国 | 6.2% |
| 法国 | 4.5% |

出口品类结构（海关总署 2025）：服饰鞋包及珠宝配饰 **21.8%（第一大）**、手机电脑等数码产品及配件 **16.5%**、家用办公电器及配件 **14.3%** —— 恰好对应本项目的纺织服装与电子电器。

> **结论**：本项目先做欧盟与美国两个市场，不是保守，而是对准了「出问题最多 × 中国卖家最多」的交集。这两个市场也是两套**完全不同的官方数据源**（欧盟 EUR-Lex、美国 eCFR）—— 两条链路都跑通，证明方法论可复制，换市场只需新增一个数据源适配器（详见[路线图](#路线图)）。

## 核心特点

| 特点 | 说明 |
|---|---|
| **可核验** | 每条结论强制回挂官方原文链接，拿不到链接的内容一律不输出 |
| **有时效** | 追踪法规变化，标注「已被取代」「新近修订」「过渡期安排」 |
| **可执行** | 把法律语言翻译成卖家能执行的动作（如「需加贴 CE 标识」） |
| **有边界** | 明确声明适用范围，范围外输入直接拒绝，不做硬编答案 |

## 功能模块

| 模块 | 名称 | 输入 | 输出 | 状态 |
|---|---|---|---|---|
| **M1** | 合规地图 | 商品类目 + 目标市场 | 适用法规清单：中文名 / 官方英文标题 / 官方编号 / CELEX 号 / ELI 链接 / OJ 出处 / 生效日期 / 是否仍有效 | ✅ 已实现 |
| **M2** | 变化时间线 | 商品类目 + 目标市场 + 时间窗（12 / 6 个月） | 近期变化条目：变化摘要 / 影响说明 / 生效或发布日期 / 官方链接 | ✅ 已实现 |
| **M3** | 待办清单 | 商品类目 + 目标市场 | 可执行动作 + 来源条款链接，支持导出 **CSV**（PDF 按 PRD 第 9 节本期不做） | ✅ 已实现 |
| **M4** | 对照演示 | 「儿童玩具 × 欧盟」固定题干（D4） | 双栏：通用大模型 vs 本工具；本期仅占位（未录制真实历史回放） | ✅ 占位 / 缺真实回放 |
| **M1.5** | 智能路由（原型） | 一句话业务描述（如「我要把洋娃娃卖到美国去」） | 自动识别「品类 × 市场」→ 复用 M1 确定性查表 → 判定卡：受影响法规 + 缺失资料清单 + **路由依据**；区分「说了但不支持」与「没说」；输入原文不落盘 | ✅ 原型已合入 |
| **M1.5-V** | 语音输入（M1.5 的输入端） | 一段中文语音（或直接打字） | 转写文本**回填输入框**供确认 → 复用 M1.5 判定；转写失败只解释原因，不产出任何合规结论 | ✅ 已实现（本地 Whisper / 云端 API 双后端） |
| **M5** | 区域差异对比 | 同一品类 + 欧盟/美国 | 按官方编号精确匹配共同条目，分别展示区域独有法规，并标记待核对区域 | ✅ 已实现 |
| **M6** | 多区域法规汇总 | 一个品类 + 多个目标区域 | 一次召回多个区域法规，按区域分组、保留官方来源并显示待核对数量 | ✅ 已实现 |
| **M7** | OPC 上线准备度 | 一个品类 + 多个目标区域 | 仅将已人工核对的 M3 待办按阶段编排；待核对区域显示部分状态且不生成可执行动作 | ✅ 已实现 |

> **M1.5 定位（10-15 增量）**：不追求「比通用模型搜得全、答得准」—— 公开数据领域的联网搜索会被拉平。真正的机会在「公开规则 × 企业真实业务」之间：结合产品、客户、合同、BOM、供应链和目标国家，判断**具体哪一单受影响、缺什么资料、依据是什么**。模型只做理解输入，法规结论 100% 来自核对语料 + 官方链接。详见 docs/PRD-增量-v1.2_M1.5输入驱动路由.md。

> **M1.5 判定语义（10-15 修复，5 处）**：
> - **两类失败严格分开** —— 「用户说了、但不在覆盖范围」点名原话（`bad_market` / `bad_category`，例：「识别到目标市场「日本」」）vs「用户没说」提示补充（`partial_*`）。混掉的后果：用户按提示补充「日本」后得到的还是「没确认出目标市场」，死循环。
> - **类目入口 5 个** —— 与界面下拉、`m1_map` 校验（`corpus.ENTRY_CATEGORIES`）同口径；`标签标识` / `通用` 属横切维度，不作为独立入口（PRD 第 3 节）。
> - **不变量 `ok ⇒ m1.ok`** —— 判定卡不会出现「上半张说判定成功、下半张报 M1·error」。
> - **依据可追溯** —— 判定卡分开显示模型给的「识别依据」与词典的「词典命中」「槽位来源」，不再用词典命中词冒充路由理由。
> - **降级如实标注** —— `route_via` 按「模型是否真的贡献了槽位」判定；模型调用失败时标「本地词典解析」，不会与「模型解析不可用」的提示自相矛盾。
>
> **响应提速**：保留模型解析12s超时与内存缓存；2026-10-19新入口取消启动查询及模型预热，明确条件使用本地规则。实际响应取决于输入与服务状态，自检见 `scripts/selftest_m15.py`。
>
> **时效性监控（10-16，最小可行版）**：`scripts/check_freshness.py` 定期核验 86 条官方链接（状态 / Last-Modified / 内容哈希），日志追加 `data/freshness_log.jsonl`，最新态落在 `data/freshness_latest.json` 并显示在每个结果页页脚。口径三分：可访问 / 链接异常（4xx-5xx，待复核）/ 本机网络未连通（不判死链）。全文落库与定时推送为后续路线，详见 [`docs/时效性监控.md`](docs/时效性监控.md)；比赛说明材料见 [`docs/比赛说明材料七要素.md`](docs/比赛说明材料七要素.md)。

> **语音输入（10-18）**：M1.5 的输入方式之一，**不是新的一条判定链路**。
> - **只做「声音 → 文字」** —— 转写文本回填到输入框，用户看得见、改得动，确认后才出判定；转写按钮不会自动查询，点击“发送”时才使用输入框当前文字。
> - **必须人工核对** —— 转写错误可能改变识别到的品类或市场，不能把识别结果直接当作合规结论。转写失败只返回原因，不覆盖原有输入，也不产出法规结论。
> - **双后端，零密钥可跑** —— 本地 sherpa-onnx + SenseVoice（预编译二进制，**不装 Python 库**）或云端 `/audio/transcriptions`；两者都不可用时语音入口自动置灰，打字链路完全不受影响。
> - **隐私口径** —— 应用不另存录音，转写缓存默认关闭；启用云端 ASR 时录音会发送到配置的服务，不应输入客户敏感信息。
> - **安全边界** —— 只接受 RIFF/WAVE，音频最大 10 MiB、最长 60 秒；单次转写等待上限 45 秒，最多 2 个并发任务。
> - **自检** —— `scripts/selftest_voice.py`（23 项，含后端缓存隔离及来源标注）、`scripts/selftest_asr_safety.py`（22 项）和 `scripts/selftest_voice_confirmation.py`（两步确认回归），均已并入 `selftest_all.py` 发布门禁。

## 技术架构

```
官方数据源（EUR-Lex · FDA · FCC · CPSC）
        │  确定性程序：抓取、解析、去重、URL 有效性校验、按类目建索引
        ▼
   法规语料库（含元数据：发布日期、生效日期、适用日期、官方链接）
        │  结构化检索：按「类目 + 市场」标签精确筛选（小规模强结构化语料，无需向量检索）
        ▼
   LLM 生成层
        · 条款筛选归类  → M1 清单
        · 变化对比与摘要 → M2 时间线
        · 法规语言 → 待办动作 → M3 清单
        │  确定性程序：引用对齐（每条输出必须回挂官方链接，无链接不输出）
        ▼
   Web 界面（部署于 ModelScope 创空间）+ 对照演示模块（M4）
```

### AI 与确定性代码的分工

| 环节 | 由谁完成 | 原因 |
|---|---|---|
| 理解、归类、摘要、翻译 | **LLM** | 这是语言任务，LLM 擅长 |
| 抓取、URL 校验、引用对齐、缓存去重 | **确定性代码** | 这些要求准确性，不能交给概率模型 |

> **设计原则**：LLM 只做「理解」类工作，凡是要「准确」的环节全部交给确定性代码。这是本产品可信度的技术基础。

### 一次查询的完整链路

```
① 用户输入        品类（如「儿童玩具」）+ 市场（如「欧盟」）
        ▼
② 结构化查表      确定性代码按「类目」「机构」两列筛选语料库
  （确定性）        · 纯本机操作，不联网、零 API 成本、毫秒级返回
        ▼
③ 结果集送 LLM    把命中的法规原文数据交给大模型组织成中文
  （LLM）           · 硬约束：只能使用给定内容，不得补充自行「知道」的法规
        ▼
④ 引用对齐        确定性程序逐条校验输出是否回挂官方链接
  （确定性）        · 无链接的条目一律不输出 —— 这是不可砍的底线
        ▼
⑤ 输出            法规清单（M1）/ 变化时间线（M2）/ 待办清单（M3）
```

**为什么不用向量检索（RAG）？**

| 对比 | 本期语料的实际情况 |
|---|---|
| 语料规模 | 仅 86 条，**小规模** |
| 数据结构 | 每条都有严格的结构化标签（类目、机构、编号），**强结构化** |
| 结论 | 按标签**精确筛选**，比向量检索更准、更快、零成本，且结果 100% 可解释（能追到具体是哪一行数据） |

> 向量检索适用于大规模非结构化语料；本项目是「小规模 + 强结构化」，用精确筛选才是对的技术选择。

**这套设计的额外好处**：即使大模型调用失败或配额耗尽，程序依然能输出原始法规清单（只是没有中文润色）—— **演示不会因 API 问题而中断**。

## 魔搭部署与版本核验

当前采用 Python + Gradio，`app.py` 转发到 `app_main.py`，默认构建 `ui_chat.py` 聊天界面。原七模块及自然语言、可选语音输入保留，M4仍缺真实回放。模型只辅助输入理解与可选摘要，失败回到本地规则。

- 根目录 `ms_deploy.json` 使用官方 schema、CPU资源、Python 3.11镜像和 Gradio 6.2.0；`requirements.txt` 与SDK版本一致。以目标空间实际资源选项和费用显示为准。
- 服务监听 `0.0.0.0`，端口优先 `PORT`、其次 `SERVER_PORT`、默认 7860。已有空间需要在设置中核对 SDK、版本和基础镜像；上传 JSON 本身不证明设置已生效。
- 登录有写权限的目标空间，复制其实际Git仓库地址，不根据展示名猜地址。最终上传源固定为 `E:\workbuddy\2026-10-14-01-02-52\compliance-radar`。
- 必需内容包括 `app.py`、`app_main.py`、`ui_chat.py`、`assets/`、`requirements.txt`、`ms_deploy.json`、完整 `core/`、`modules/`、主CSV、`data/snapshot.json`、`data/journey_sources.json`。推荐从根目录使用 `scripts/prepare_release.py` 生成完整源码ZIP。

### 语音输入（可选，不装也能跑）

语音是**可选入口**：本地引擎未准备且未配置云端 ASR 时，语音入口自动置灰，文字输入仍可使用。

**默认引擎：sherpa-onnx + SenseVoice（不装任何 Python 库）**

```powershell
# ① 一条命令准备引擎与模型（sherpa-onnx 预编译二进制 + SenseVoice int8，约 250MB，只需一次）
.\.venv\Scripts\python.exe scripts\prepare_asr_engine.py

# ② 检查是否就位（不下载）
.\.venv\Scripts\python.exe scripts\prepare_asr_engine.py --check

# ③ 起界面，在折叠的语音输入区录音或上传
.\.venv\Scripts\python.exe app.py
```

引擎落在 `models/sherpa-onnx/`（已在 `.gitignore` 中排除，不进仓库）。`core/asr_engine.py` **只用标准库**
（`subprocess` / `urllib` / `tarfile`）起子进程，不引入 `faster-whisper`、`av`、`torch` 等任何 Python ASR 库。

**为什么换引擎**：中文短句 + 领域词场景下，SenseVoice 是官方实测 CER 7.81% 的候选（Whisper-large-v3 为 20.02%），
支持中/英/日/韩/粤（中英混说不用切语言），CPU 上更快，且省掉了 `av<19` 那套版本锁。

**想走云端而不下模型**（零新增依赖，配置以下4项；在 `.env` 中填写实际服务）：

```bash
ASR_BACKEND=cloud
ASR_API_BASE=https://<你的服务>/v1
ASR_API_KEY=<key>
ASR_MODEL=<whisper-1 之类的模型名>
```

**后端优先级**（`ASR_BACKEND=auto` 时）：云端（显式配置才生效）→ sherpa-onnx 引擎 → 本地 Whisper → 关闭。

**关键约定**：

- **常驻服务**：应用启动时后台拉起 `sherpa-onnx-offline-websocket-server`，模型只加载一次；
  单句转写从约 3 秒降到约 0.3 秒（本机 Windows / 2 线程实测）。服务起不来时自动退回命令行
  冷启动，只慢不坏；`ASR_ENGINE_SERVER=off` 可关掉。
- **预编辑（preedit）**：识别结果先进入输入框做"未提交"的草稿——可直接改字，
  状态条显示 `预编辑 · 未提交`；点「撤销识别」可回到识别前的文字（改过字则不再覆盖）。
  只有点「发送」才算提交，转写本身不发起任何查询。
- 转写文本**只回填到输入框**，不直接出结论，用户检查、修改后再点“发送”。
- 语音链路失败（引擎没准备、麦克风没权限、网络断）**只降级提示**，不抛异常、不污染已有输入。
- 转写缓存默认关闭；显式启用后仅缓存转写文本和必要元数据，缓存键隔离音频摘要、后端、模型与语言。录音由界面临时存储，本应用不另存音频；云端转写会将录音发送到配置的服务。
- 引擎下载走 GitHub Releases；国内网络不顺时可换镜像：`--mirror https://gh-proxy.com/https://github.com/k2-fsa/sherpa-onnx/releases/download`。
- 历史后端 `faster-whisper`（`ASR_BACKEND=local`）仍保留作兜底，但**不再推荐**：需要 pip 依赖且精度更低。

> 📖 **每个 `.py` 文件分别怎么跑、跑了有什么用 —— 见 [`docs/07-运行指南.md`](docs/07-运行指南.md)。**

### 什么算「官方来源」

三个条件缺一不可：

| 要素 | 判定标准 |
|---|---|
| **域名** | 必须是 `eur-lex.europa.eu`（欧盟）或对应国家监管机构官方域名；ELI 永久标识可为 `data.europa.eu/eli/...` |
| **法源** | 落在《欧盟官方公报》（Official Journal, OJ）等官方公报上公布的文本 |
| **标识** | 能找到 **CELEX 号**与 **ELI 标识**，且编号能对回官方公报 |

### 明确不算官方来源

- 第三方法律数据库、律所或媒体解读、百科条目
- AI 生成的摘要
- 官方站的「解读性摘要」页（属官方摘要，非法条原文）
- 无 CELEX / ELI 标识、或点进去回不到原文的链接

> 📖 详细规则见 [`docs/04-官方来源判定指南.md`](docs/04-官方来源判定指南.md)

### 关于「链接打不开」的判定规则

官方站点（欧盟 EUR-Lex、美国 FDA / FTC / CPSC / FCC 等）普遍部署了人机验证墙或访问限制，**程序化访问常被拦截**（返回 202 挑战页、403，或指向误导页），但**真人在浏览器中可正常打开**。

| 情况 | 判定 |
|---|---|
| 程序访问被拦（202 / 403 / 异常跳转） | **不等于链接失效** —— 记「需人工浏览器验证」 |
| 真人浏览器也打不开 | 才是真的链接有问题 |

**规则：真人浏览器能打开的一律记为「可打开」，不因程序报错就判定链接失效、更不要因此去改链接。**

**M1.5 实现明细（输入驱动路由）**：

- `modules/m15_router.py` 两级解析：① 模型解析（`PARSE_PROMPT` 严格 JSON，`temperature=0`，`use_cache=False`——输入原文不落盘）② 本地词典兜底（子串匹配，零依赖、不联网）。任一级失败自动落到下一级，两级都失败则诚实拒绝
- **类目枚举由 `corpus.SUPPORTED_CATEGORIES` 动态生成**，校验用 `corpus.ENTRY_CATEGORIES`（5 个）—— 与界面下拉、`m1_map` 同口径，不再多处硬编、避免漂移
- **「范围外」哨兵**：模型用 `范围外` 表达「用户说了但不支持」，与空字符串「用户没说」严格区分。词典路径靠一张**只用于点名、不参与路由决策**的范围外词表取得同样效果（PRD 验收用例 7 要求无模型链路时行为照常）。该词表只在受支持词表零命中时才查，漏词只会让拒绝理由说得含糊，不会答错
- **不变量 `ok ⇒ m1.ok`**：查表失败一律不许声称成功
- **`max_tokens=4000`**：本链路默认模型是推理模型，`reasoning` 计入 `max_tokens`；给 300 会返回空内容并静默降级到词典（实测 300/400 必然空返回、600 时 JSON 被截断）
- **渲染安全**：模型回显的用户原文（识别依据 / 用户品类 / 用户市场）进 `gr.HTML` 前一律 `html.escape`
- 自检：`python modules/m15_router.py`（词典路径，离线确定性）+ `python scripts/selftest_m15.py`（模型路径，桩注入 `llm.chat` / `llm.is_ready`）。模型路径即使 `temperature=0` 也不确定，故**不用真实模型做断言**
