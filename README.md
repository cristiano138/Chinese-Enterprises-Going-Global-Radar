# ComplianceRadar 出海合规雷达

> **Sellers enter "what I sell + where I sell it" → get which regulations apply, what changed recently, and what to do next — every conclusion backed by a link to its official source.**

面向出海卖家的法规合规自查工具。输入「商品类目 + 目标市场」，输出**适用法规清单 · 法规变化时间线 · 可执行待办清单**，**每条结论强制附官方原文链接**。

## 这个项目解决什么问题

### 场景

一个卖家要把商品卖到海外市场，必须先搞清楚：**我这个品类，目标市场有哪些法规要求？最近有没有变化？我现在要做什么准备？**

### 现状有多难

| 痛点 | 具体表现 |
|---|---|
| **法规分散** | 各国官网各查一遍，欧盟要查 EUR-Lex，美国要分别查 FDA / FCC / CPSC |
| **语言与专业门槛** | 全是英文法律术语，非专业背景根本读不懂 |
| **更新跟不动** | 法规频繁修订甚至整部被取代，卖家往往事后才知道 |
| **通用 AI 不可靠** | 直接问大模型容易编造条款号、引用已被废止的旧法规，且不给来源 |

### 一个真实案例

欧盟儿童玩具法规已经更替：

- **Regulation (EU) 2025/2509** 于 2025-11-26 通过，**2026-01-01 生效**
- 将于 **2030-08-01 起全面取代** 沿用十余年的 **Directive 2009/48/EC**

一个做了十几年玩具出口的卖家，如果现在还按旧指令准备合规，就选错了标准。而直接问通用大模型，它多半还会回答已经过时的 `Directive 2009/48/EC`，且不提供来源链接。

**这正是本工具的切入点：让法规变化可见，让每条结论可核验。**

## 核心特点

| 特点 | 说明 |
|---|---|
| **可核验** | 每条结论强制回挂官方原文链接，拿不到链接的内容一律不输出 |
| **有时效** | 追踪法规变化，标注「已被取代」「新近修订」「过渡期安排」 |
| **可执行** | 把法律语言翻译成卖家能执行的动作（如「需加贴 CE 标识」） |
| **有边界** | 明确声明适用范围，范围外输入直接拒绝，不做硬编答案 |

## 功能模块

| 模块 | 名称 | 输入 | 输出 |
|---|---|---|---|
| **M1** | 合规地图 | 商品类目 + 目标市场 | 适用法规清单：中文名 / 官方英文标题 / 官方编号 / CELEX 号 / ELI 链接 / OJ 出处 / 生效日期 / 是否仍有效 |
| **M2** | 变化时间线 | 商品类目 + 目标市场 | 近期变化条目：变化摘要 / 影响说明 / 生效或发布日期 / 官方链接 |
| **M3** | 待办清单 | 商品类目 + 目标市场 | 可执行动作 + 来源条款链接，支持导出 |
| **M4** | 对照演示 | 同一问题 | 双栏对比：通用大模型直答 vs 本工具 |

## 技术架构

```
官方数据源（EUR-Lex · FDA · FCC · CPSC）
        │  确定性程序：抓取、解析、去重、URL 有效性校验、按类目建索引
        ▼
   法规语料库（含元数据：发布日期、生效日期、适用日期、官方链接）
        │  检索增强（RAG）：按「类目 + 市场」检索相关条款
        ▼
   LLM 生成层
        · 条款筛选归类  → M1 清单
        · 变化对比与摘要 → M2 时间线
        · 法规语言 → 待办动作 → M3 清单
        │  确定性程序：引用对齐（每条输出必须回挂官方链接，无链接不输出）
        ▼
   Web 界面（部署于 ModelScope 创空间）+ 对照演示模块（M4）
```

### AI 与确定性代码的分工

| 环节 | 由谁完成 | 原因 |
|---|---|---|
| 理解、归类、摘要、翻译 | **LLM** | 这是语言任务，LLM 擅长 |
| 抓取、URL 校验、引用对齐、缓存去重 | **确定性代码** | 这些要求准确性，不能交给概率模型 |

> **设计原则**：LLM 只做「理解」类工作，凡是要「准确」的环节全部交给确定性代码。这是本产品可信度的技术基础。

## 快速开始

> ⚠️ 代码实现正在进行中（截至 2026-10-14）。以下为规划中的使用方式。

### 环境要求

- Python 3.10+
- 可访问官方数据源

### 安装

```bash
git clone https://github.com/<your-username>/compliance-radar.git
cd compliance-radar
pip install -r requirements.txt
```

### 配置

复制环境变量模板，填入你的 API Token：

```bash
cp .env.example .env
# 编辑 .env，填入 MODEL_API_TOKEN
```

> 🔒 **安全提示**：API Token 必须通过环境变量传入，不要写死在代码里。本项目已在 `.gitignore` 中排除 `.env`。

### 运行

```bash
python app.py
```

浏览器打开提示的本地地址即可使用。

## 数据来源与引用规范

### 本期覆盖范围

| 项 | 范围 |
|---|---|
| 市场 | 欧盟（EU）+ 美国（US） |
| 品类 | 儿童玩具、电子电器、纺织服装、美妆个护、食品接触材料 |
| 合规维度 | 产品安全法规、标签标识 |

### 什么算「官方来源」

三个条件缺一不可：

| 要素 | 判定标准 |
|---|---|
| **域名** | 必须是 `eur-lex.europa.eu`（欧盟）或对应国家监管机构官方域名；ELI 永久标识可为 `data.europa.eu/eli/...` |
| **法源** | 落在《欧盟官方公报》（Official Journal, OJ）等官方公报上公布的文本 |
| **标识** | 能找到 **CELEX 号**与 **ELI 标识**，且编号能对回官方公报 |

### 明确不算官方来源

- 第三方法律数据库、律所或媒体解读、百科条目
- AI 生成的摘要
- 官方站的「解读性摘要」页（属官方摘要，非法条原文）
- 无 CELEX / ELI 标识、或点进去回不到原文的链接

> 📖 详细规则见 [`docs/04-官方来源判定指南.md`](docs/04-官方来源判定指南.md)

## 路线图

### 本期实现

- 2 个市场（欧盟 + 美国）× 5 个品类
- 2 个合规维度（产品安全法规 + 标签标识）
- 4 个功能模块（M1–M4）

### 后续规划

| 方向 | 内容 |
|---|---|
| **多市场** | 扩展至英国（UKCA）、日本（PSE/PSC）、东南亚、中东 |
| **多维度** | 税务合规（VAT）、知识产权、海关清关、数据合规 |
| **全流程** | 检出问题后就近对接检测机构 / 律师 / 货代 |
| **行业专版** | 玩具版、电子版、纺织版、美妆版、食品接触材料版 |
| **订阅服务** | 法规变化主动推送 |

**架构上的可扩展性**：

| 扩张方向 | 架构支撑 |
|---|---|
| 加市场 | 数据源做成适配器模式，新增市场 = 新增适配器 |
| 加品类 | 语料库按类目标签索引，新增品类 = 新增标签 |
| 加维度 | 模块按查询维度解耦，新增维度 = 新增模块 |
| 加能力 | 前端按结果卡片组合，新增能力 = 新增卡片 |

## 合规声明

- 本项目仅使用**公开的法规数据**（欧盟 EUR-Lex、美国监管机构官网等官方公开渠道），**不采集任何个人信息**。
- 本项目输出的合规清单**仅供参考，不构成法律意见**，使用者应咨询专业机构并由专业人员复核。
