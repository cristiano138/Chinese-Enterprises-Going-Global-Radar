# 法规材料落库链路（新法规 / 变更）

版本：2026-10-18 ｜ 关联：`core/law_intake.py`、`scripts/ingest_law_material.py`、
`scripts/refresh_recall_pipeline.py`、`scripts/build_recall_tree.py`

## 1. 一句话

时效性脚本或搜索校验 agent 发现新法规/变更后，沿着：

```text
发现
  -> laws 骨架建档（core.law_intake）
  -> 材料 manifest 落库（documents / law_documents / units）
  -> 召回树全量重建 + 校验
  -> core.recall / modules.recall_flow 可检索
```

把材料补进 SQLite，并让新法规立刻进入召回链路。**本链路不做向量召回。**

## 2. 各环节与命令

### ① 发现（已有）

- `scripts/check_metadata_freshness.py`：核验 86 条法规的官方字段，自动更新
  `laws` 表，写 `data/freshness_latest.json`（含 `changes[].law_id`）和
  `data/freshness_log.jsonl`。
- 搜索校验 agent：发现库外新法规时，调用 `core/law_intake.py` 建档，并写
  `sqlite/law_intake_log.jsonl`（`action="inserted"`、`law_id`）。

### ② 骨架建档（已有）

```python
from core import law_intake
law_intake.intake_eu_law("32026R9999", category="儿童玩具", note="...")
law_intake.intake_us_law(16, "9999", category="电子电器", agency="CPSC")
```

只建 `laws` 行，不抓全文、不切 units。新法规在 `units` 表没有记录是预期状态。

### ③ 材料落库（新增）

agent/外部解析器把抓到的全文和切片整理成一个 **manifest JSON**，交给：

```bash
python scripts/ingest_law_material.py --manifest data/material_tasks/EU_32026R9999.json --dry-run
python scripts/ingest_law_material.py --manifest data/material_tasks/EU_32026R9999.json
python scripts/ingest_law_material.py --manifest data/material_tasks/EU_32026R9999.json --rebuild
```

manifest 最小结构：

```json
{
  "law_id": "EU:32026R9999",
  "documents": [{
    "id": "EU-DOC:32026R9999",
    "kind": "eu_original",
    "source_identifier": "32026R9999",
    "official_title": "Regulation (EU) 2026/9999 ...",
    "language": "en",
    "version_date": "2026-01-01",
    "publication_date": "2026-01-01",
    "legal_status": "current",
    "source_url": "https://eur-lex.europa.eu/...",
    "full_text": "...",
    "role": "primary",
    "replace_units": true
  }],
  "units": [{
    "document_id": "EU-DOC:32026R9999",
    "ordinal": 0,
    "locator": "https://...#art_1",
    "unit_type": "article",
    "heading": "Article 1 — Subject matter",
    "body": "Article 1\nSubject matter\n...",
    "source_fragment": "<html:div ...>"
  }]
}
```

落库语义：

- `documents` / `law_documents` / `units` 全部 upsert；`law_documents.role` 默认
  `primary`，允许 `eu_consolidated` / `eu_amendment` / `eu_corrigendum` /
  `rule_publication` / `bulk_fallback` / `annual_reference` / `cited_source_reference`。
- `replace_units=true`（默认）：先删该文档旧 units，再写 manifest units。
  适用于“重新解析整篇”的变更。
- `replace_units=false`：只 upsert manifest 里的 units，保留旧 units。
  适用于增量追加。
- 单事务写入；校验失败不落库。
- 只更新 `laws` 已存在的法规；新法规请先走 `law_intake`。

### ④ 编排 / 状态检查 / task（新增）

```bash
# 只看状态，不写库
python scripts/refresh_recall_pipeline.py --law-id EU:32026R9999 --dry-run

# 从时效性报告或 intake 日志批量取目标
python scripts/refresh_recall_pipeline.py --changed-file data/freshness_latest.json --rebuild
python scripts/refresh_recall_pipeline.py --from-intake-log --rebuild
```

状态：

| 状态 | 含义 | 编排器动作 |
|---|---|---|
| `ready` | canonical 文档有 ≥5 个结构化 units | 可选全量重建 |
| `thin` | 1–4 个结构化 units | 仍可建树，标 thin |
| `no_structured` | 有 units 但没有 article/annex/section/subpart/appendix | 树走全文兜底 |
| `material_missing` | 没有 documents 或 units 为 0 | 写 `material_intake` pending task |
| `missing_law` | `laws` 表没有该 id | 写 task，提示先 `law_intake` |

材料缺失时，编排器会：

- 在 `tasks` 表 upsert：
  `task_key="material:<law_id>"`、`phase="material_intake"`、`state="pending"`，
  `payload_json` 里带 law 元数据、来源链接、必需字段和 manifest 模板；
- 写 `data/material_tasks/<safe_law_id>.json`（同 payload），方便 agent 直接读；
- 不触发重建（避免用空材料建出无意义节点）。

材料到位后，编排器把对应 task 标为 `done`；`--rebuild` 会调用
`scripts/build_recall_tree.py --db <db>` 做**全量重建**（86 法约 5 秒），
并可选 `--check`。

### ⑤ 重建召回树（已有）

```bash
python scripts/build_recall_tree.py --db <db> --report data/recall_tree_report.json
python scripts/build_recall_tree.py --db <db> --check
```

新法规的 `primary`/`eu_consolidated` 文档会被 canonical 选择规则纳入；
units 结构决定它是 article/annex/section/subpart 树还是全文兜底。
重建后 `core.recall.law_catalog()`、`candidate_nodes()` 立即能看到新法规。

### ⑥ 检索（已有）

```python
from modules import recall_flow
res = recall_flow.run("新法规涉及的产品和问题")
```

路由 LLM 的目录、检索 LLM 的候选、`citation_map` 都来自重建后的树。

## 3. 表契约

### documents

必需：`id`、`jurisdiction`（从 laws 取）、`kind`、`source_identifier`、
`legal_status`、`source_url`。
可选：`official_title`、`language`（默认 en）、`version_date`、
`publication_date`、`full_text`、`notes`。
默认：`metadata_status=pending`、`transfer_status=pending`、
`parse_status=extracted_unreviewed`。

### law_documents

`(law_id, document_id, role)`。召回树只用 `primary` / `eu_consolidated`；
其他角色保留用于时效性/修订追查。

### units

`(document_id, ordinal)` 主键；必需 `locator`、`unit_type`、`body`；
`heading` 可选（没有标题时树会标 `label_only`）；`source_fragment` 可选
（用于补标题，不建议把超大 HTML 全塞进 manifest，可按需截取）。

结构化类型：`article` / `annex` / `section` / `subpart` / `appendix`。
`pdf_page` / `n` / `text_block` / `auth` / `source` / `preamble` 不进树。

## 4. 新法规完整示例

```bash
# 1) agent 发现新法规，建档
python -c "from core import law_intake; print(law_intake.intake_eu_law('32026R9999', category='儿童玩具'))"

# 2) 编排器检查：此时 material_missing，生成 task
python scripts/refresh_recall_pipeline.py --law-id EU:32026R9999

# 3) agent 抓取 EUR-Lex 全文并解析成 units，写 manifest
#    参考 data/material_tasks/EU_32026R9999.json 的 manifest_template

# 4) 材料落库（可选 --rebuild）
python scripts/ingest_law_material.py --manifest data/material_tasks/EU_32026R9999.json --rebuild

# 5) 确认状态并校验
python scripts/refresh_recall_pipeline.py --law-id EU:32026R9999 --dry-run
python scripts/build_recall_tree.py --check
```

## 5. 变更/修订示例

- **EU 新增 consolidated（现行合并文本）**：manifest 里加一份
  `role="eu_consolidated"` 的文档，`replace_units=true`；编排器重建后，
  canonical 选择规则会优先用它。
- **US 新增 FR 规则发布**：manifest 里加 `role="rule_publication"` 的文档；
  v1 基础树不包含修正案，但文档/units 留存，供时效性和未来 § 级切分使用。
- **原文重解析**：同一 `document_id` + `replace_units=true`，整篇替换 units。

## 6. 当前边界（必须知道）

1. **仓库里没有自动的 EU/US 全文抓取 + units 解析器**。现有 86 法的 units
   来自仓库外的人工/半自动流程（`core/law_intake.py` 头部已注明）。
   本链路提供的是**落库契约和编排**，抓全文/切 units 仍由 agent 或外部解析器
   完成；manifest 是它们与数据库之间的稳定接口。
2. **全量重建**：v1 没有按法规增量重建；每次 `--rebuild` 重建全部 86 法
   （约 5 秒）。法规量增长后再加 scoped rebuild。
3. **不做向量召回**：检索层仍是 FTS/BM25 + 编号 ref + LLM 选择。
4. **修正案不进基础树**：v1 只建现行法规树；EU 用 consolidated，US 用 eCFR
   primary。新增修正案文档先落库留档，不自动进树。
5. **人工复核**：manifest 落库后建议抽查 `units` 的 ordinal/heading/body，
   再跑 `build_recall_tree.py --check`；不要直接信任外部解析器的输出。

## 7. 验收

```bash
python scripts/selftest_material_pipeline.py   # 19 项：manifest/落库/task/重建
python scripts/selftest_recall.py              # 51 项：树构建/访问层
python scripts/selftest_recall_flow.py         # 33 项：两层召回
python scripts/selftest_all.py                 # RELEASE GATE 全绿
```

新法规落库后，重点看：

- `refresh_recall_pipeline.py` 状态从 `material_missing` 变为 `ready`/`thin`；
- `tasks` 表对应 task 从 `pending` 变 `done`；
- `build_recall_tree.py --check` 通过；
- `core.recall.law_catalog()` 能看到新 law_id；
- `recall_flow.run()` 的 route/retrieval 能命中新法规。
