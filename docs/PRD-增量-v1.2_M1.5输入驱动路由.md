# PRD 增量 v1.2 · M1.5 输入驱动路由（公开规则 × 企业真实业务）

版本：2026-10-15（北京时间）｜状态：本期实施（与 M2/M3 并行，由李随 M2/M3 合入）
来源：李的方案（DeepSeek 做路由层）+ 队长评审意见（10-15）+ 参考站勘察（水则 / 法小通）

## 1. 为什么做（产品定位修正）

- **不把「比通用模型搜得全、答得准」当核心优势**：公开数据领域的联网搜索会很快被拉平。
- 真正的机会在「公开规则 × 企业真实业务」之间这一层：同一条欧盟法规，
  不是给企业解释法规，而是结合它自己的**产品、客户、合同、BOM、供应链和目标国家**，
  判断**具体哪一单、哪一个产品受影响，缺什么资料，依据是什么，谁需要处理**。
- 因此最终形态不是「合规聊天机器人」，而是：
  **合规工作流 + Evidence + 企业数据治理 + 持续监控** 的系统。
  M1.5 是这条路上的第一小步（4 天工期内的最小实现，不引入复杂度）。

## 2. 与既有红线的关系（全部不变）

- 法规结论 100% 来自本地核对语料表（86 条）+ 官方链接；引用对齐、免责声明不砍。
- 模型只做「理解、归类」—— 即**路由**；无权新增 / 改写 / 编造任何法规。
- M1 下拉查表保留（演示主流程「儿童玩具 × 欧盟」不受影响）；M1.5 是**新增页签**。
- M2 / M3 严格按 docs/PRD-定稿.md 执行，本增量不改动其任何定义。

## 3. 功能定义（M1.5）

**输入：**一句大白话业务描述（如「我要把洋娃娃卖到美国去，要做哪些合规工作」）
+ 选填企业上下文（产品材质 / 客户要求 / 合同关键信息）。

**处理（两级解析，逐级降级，演示永不中断）：**

1. 模型解析：LLM 从输入抽「品类 / 市场」槽位（严格 JSON，temperature=0）；
2. 本地词典解析：关键词匹配（确定性代码，零依赖、零成本，永不失败）；
3. 任一级失败自动落到下一级；两级都失败 → **诚实拒绝**并展示支持范围（不硬编答案）。

**输出（判定卡）：**

- a. 识别结果：品类 × 市场 + 路由方式如实标注（模型解析 / 本地词典解析 / 混合）
- b. 受影响法规清单：**复用 M1 确定性查表**（含横切法规与引用对齐，逐条官方链接）
- c. 缺失资料清单：该品类判定还缺的关键资料（如玩具的适用年龄段、材质 / 电池结构、
   已有测试报告、标签稿）—— 这是 M3 待办清单的「输入侧」接口
- d. 通用补充：产品 BOM / 材质单、合同或客户合规要求、供应链分工
   （本期仅提示，不做结构化判定）

## 4. 隐私与企业数据治理（最小可行演示）

这是与通用对话产品拉开差距的门槛之一，本期做「最小可信演示」：

| 层 | 规则 |
|---|---|
| 能给模型看 | 用户主动输入的业务描述文本 + 槽位化后的「品类 / 市场」 |
| 不落盘 | 路由调用禁用 LLM 磁盘缓存（`use_cache=False`）；输入原文只在内存中处理 |
| 不收集 | 不采集卖家个人信息（对齐 PRD-定稿 第 7 节）；上下文仅辅助识别、不存储 |
| 页面提示 | 固定红字：请勿输入个人隐私与客户敏感信息 |
| 待做（本期不做） | 本地处理 / 脱敏分级、权限体系、结论溯源报告（写进七要素「转化路径」） |

## 5. 模型链路

- 复用 `core/llm.py` 既有 OpenAI 兼容链路（`MODEL_API_BASE` / `MODEL_API_TOKEN` / `MODEL_NAME`）。
- 李的方案「申请 DeepSeek API」= 把上述环境变量指到 `https://api.deepseek.com`，
  `MODEL_NAME=deepseek-chat`（或 `deepseek-reasoner`）。
- **未配置也照常跑**（词典兜底），创空间演示不依赖任何付费 API。
