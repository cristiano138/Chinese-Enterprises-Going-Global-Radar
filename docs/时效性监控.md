# 时效性监控 · 设计说明（团队新思路的可行性收敛）

版本：2026-10-16 ｜ 状态：最小可行版已落地（`scripts/check_freshness.py`）

## 1. 原始思路与本期收敛

团队提出的方向：法规落到本地（全文 + 元数据落库）、每天定时查欧美两个市场的法规时效、
查询动作写日志、后期把日志做成用户可见，形成「时效性优势」。

方向认可 —— 它正是产品定位里「持续监控」这一差异化支柱。按 4 天工期做可行性收敛：

| 原思路 | 本期做什么 | 为什么收敛 |
|---|---|---|
| 法规全文落库 | **不做**。只监控 86 条官方链接的元数据（HTTP 状态 / Last-Modified / 内容哈希） | 全文抓取涉及 EUR-Lex 反爬、PDF 解析、存储与版权边界，4 天内做不稳；元数据级监控已能回答「链接活没活、内容变没变」 |
| 每天定时查时效 | **脚本就绪 + 定时方案给出**（Windows 计划任务 / cron，见脚本 docstring），演示前手动/本地定时跑 | 线上创空间无 cron 入口；脚本一次全量核验约 1~2 分钟，任何机器都能跑 |
| 查询动作写日志 | **已做**：`data/freshness_log.jsonl` 每次核验每链接追加一行，可审计可回放 | JSONL 追加写最简单可靠，后期可直接接到用户可见的时间线 |
| 日志用户可见 | **已做（摘要级）**：所有结果页页脚展示「最近核验时间 · 可访问/异常数 · 内容更新数」 | 全文级 diff 展示留给后续；摘要徽章足以支撑「持续监控」的演示叙事 |

## 2. 数据流

```
scripts/check_freshness.py（手动 / 计划任务 / cron）
    │  读取 core/corpus.py 的 86 条官方链接（官方链接 + ELI 链接，去重）
    │  并发 8 路 GET（每链接 15s 超时，只读前 128KB 算 sha256）
    ▼
data/freshness_log.jsonl     ← 追加：每链接一行 {ts, url, status, hash, ok, changed, ...}
data/freshness_latest.json   ← 覆盖：最新一次的汇总 + 每链接记录
    ▼
app_main.py 页脚徽章（_freshness_footer，按文件 mtime 记忆化读取）
    文件不存在 → 静默不显示（不硬编、不假装验过）
```

「内容有更新」判定：与上一次核验的内容哈希比对，哈希不同即标 `changed`。
注意这是「页面字节变了」，不等于「法规条文变了」—— 条文级变更仍归 M2 时间线人工核对。

## 3. 与红线的关系

- 监控只访问**官方公开链接**，不引入任何非官方来源；
- 核验结果只是「链接状态证据」，**不构成法规结论**——结论仍 100% 出自核对语料表；
- 徽章如实显示核验时间与异常数，异常不遮掩（WAF 拦截等失败同样入日志）。

## 4. 后续路线（本期明确不做）

1. 全文快照落库（本地 data/snapshot/，按日期留档，支撑 diff 级监控）；
2. 创空间侧定时触发（平台支持后接入，或改由 GitHub Actions 每日跑 + 回写仓库）；
3. 变更摘要推送给用户（邮件 / 飞书 webhook）；
4. 「查询动作日志」扩展到用户查询侧（需先做隐私评审，默认不记录输入原文）。
