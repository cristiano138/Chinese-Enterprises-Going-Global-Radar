### 🎯 最重大的发现：EUR-Lex 设了「人机验证墙」

**根因已查清**（10.14 17:32）：抓到的那 2035 字节内容里含 `awswaf.com`、`challenge.js` 等关键字。

> **EUR-Lex 用 AWS WAF 的 JavaScript 挑战做防护。curl 这类命令行工具不会执行 JS，因此永远拿不到页面内容。**

**这解释了两件事**：
1. 为什么 curl 直抓永远返回 202 空 —— **不是反爬规则，是"你是真人吗"的验证墙**
2. 为什么**开不开 VPN 完全没区别** —— **跟网络位置无关，是站点自己的防护机制**

**结论：不要浪费时间在"爬 EUR-Lex 网页"上，此路不通。**

## 一、这一关要验什么（判定标准）

**目标：确认每个数据源，能不能稳定拿到「官方链接 + 官方编号」这两样东西。**

拿到 = 通过；拿不到 = 换通路；全换不通 = 收缩范围。

### 合格标准（三条，缺一不可）

| 项 | 合格 | 不合格 |
| --- | --- | --- |
| **链接域名** | 官方域名（欧盟 `eur-lex.europa.eu` / 美国 `.gov`） | 律所站、聚合库、百科、AI 摘要站 |
| **编号** | 能拿到 CELEX 号（欧盟）/ 法规编号（美国） | 只有标题没有编号 |
| **可定位到原文** | 链接点开能到法条原文页 | 只到首页/搜索页/摘要页 |

### 废掉的标准（遇到就换通路，别硬扛）

- 返回 **HTTP 202 / 403 / 400 且内容为空** → 反爬拦截
- 只给 **PDF 不给 HTML** → 需额外解析，成本高（但可接受，见下）
- 只给 **摘要/整合版** → 不能作为唯一依据，必须另找 OJ 原文
- 要求 **登录/验证码** → 该通路废弃

## 二、欧盟通路（EUR-Lex）—— ✅ 已实测，两条可用通路

### 2.1 ⭐⭐⭐ 主通路：SPARQL 官方数据接口（最优）

**这是欧盟通路的最强武器。** 网页有 WAF 墙，但官方数据接口是开放的。

**接口**：`https://publications.europa.eu/webapi/rdf/sparql`

**怎么用（三步）**：

1. **先拿到 Cellar URI**：用 CELEX 号查
   ```sparql
   PREFIX cdm: <http://publications.europa.eu/ontology/cdm#>
   SELECT ?work ?title ?date WHERE {
     ?work cdm:resource_legal_id_celex "32025R2509" .
     OPTIONAL { ?work cdm:work_date_document ?date }
     OPTIONAL { ?work cdm:work_title ?title }
   } LIMIT 10
   ```
   → 拿到 `http://publications.europa.eu/resource/cellar/f2294563-...`

2. **用 Cellar URI 查全部字段**：
   ```sparql
   SELECT ?p ?o WHERE { <上面的cellar-uri> ?p ?o } LIMIT 80
   ```
   → 拿到 CELEX、ELI、生效日期、是否有效、取代关系……

3. **URL 编码后调接口**：
   ```
   https://publications.europa.eu/webapi/rdf/sparql?query={URL编码}&format=application/sparql-results+json
   ```

**优点**：
- ✅ 比网页更权威（直接来自 Cellar 官方仓储）
- ✅ 结构化，不用解析 HTML
- ✅ **一次拿全所有字段**，含网页上不显示的元数据
- ✅ 无 WAF 墙、无密钥

**缺点**：
- ⚠️ SPARQL 查询语法需要学（但对 AI 来说是小事）
- ⚠️ 需要先用 CELEX 号定位 Cellar URI（两步查询）

### 2.2 辅通路：搜索引擎定位法 ✅

**当不知道 CELEX 号时，先用搜索找到它。**

1. 搜索：`EUR-Lex CELEX [编号] [法规主题] official journal`
2. 从结果里挑 `eur-lex.europa.eu` 域名的条目
3. 取：**官方链接**、**CELEX 号**、**OJ 出处**
4. 再用 2.1 的 SPARQL 接口补全其余字段

**实测耗时**：单条约 30 秒。

### 2.3 辅通路：编号拼链接法 ✅

**当已知 CELEX 号时，可以直接拼出页面链接（给人看的）**：

```
HTML 版：https://eur-lex.europa.eu/legal-content/EN/TXT/?uri=CELEX:{CELEX号}
PDF  版：https://eur-lex.europa.eu/legal-content/EN/TXT/PDF/?uri=OJ:{OJ编号}
```

**实例验证**：
- CELEX `32025R2509` → `https://eur-lex.europa.eu/legal-content/EN/TXT/?uri=CELEX:32025R2509` ✅
- OJ `L_202502509` → `https://eur-lex.europa.eu/legal-content/EN/TXT/PDF/?uri=OJ:L_202502509` ✅

> ⚠️ **注意**：拼出来的链接**给人点开可以用**（浏览器会过 WAF），但**机器抓取仍然会碰墙**。所以：**链接给用户看，数据从 SPARQL 拿。**

### 2.4 ❌ 死路（不要浪费时间）

| 通路 | 结果 | 原因 |
| --- | --- | --- |
| curl 直抓 eur-lex 页面 | 202 空 | **AWS WAF 人机验证** |
| eur-lex 的 robots.txt | 202 | 同站点级防护 |
| OJ 的 PDF 直链 | 202 空 | 同 |
| 开 VPN 后重试 | **完全一样** | **与网络位置无关，是站点自己的墙** |

**根因证据**：抓到的 2035 字节内容里含 `awswaf.com`、`challenge.js`（AWS WAF 的 JS 挑战脚本）。

### 2.5 CELEX 号结构（记牢，判断真伪用）

```
3  2025  R  2509
│   │    │   └── 序号
│   │    └────── 类型：R=Regulation(条例) L=Directive(指令) D=Decision(决定)
│   └─────────── 年份
└─────────────── 部门号：3 = 欧盟立法
```

**常见变体**：
| 形式 | 含义 | 例 |
| --- | --- | --- |
| `3YYYYRnnnn` | 欧盟条例 | 32025R2509 |
| `3YYYYLnnnn` | 欧盟指令 | 32009L0048 |
| `3YYYYDnnnn` | 欧盟决定 | 32023D0740 |
| `02009L0048-20110720` | **整合版**（非权威，注意！） | 02009L0048 |

> ⚠️ **以 `0` 开头的是整合版（Consolidated text），非权威文本。** 引用时必须回到 OJ 原文。这一条张的判定指南里也强调了。

## 三、美国通路 —— ✅ **已验证通过（10.14 17:30）**

### 🎉 最重要的发现：美国所有法规都在一个地方 —— eCFR

**CPSC / FDA / FCC 三家虽然机构不同，但它们的法规条文全部收在同一本《联邦法规汇编》（CFR）里。**

| 机构 | 管什么 | 对应 CFR | 与我们的品类 |
| --- | --- | --- | --- |
| **CPSC** | 消费品安全（含玩具！） | **Title 16** | 儿童玩具、部分电子 |
| **FDA** | 食品、药品、化妆品、食品接触材料 | **Title 21** | 美妆个护、食品接触材料 |
| **FCC** | 电子产品电磁兼容/无线 | **Title 47** | 电子电器 |

**这意味着：不用对付三个不同结构的网站，只用对付一个 eCFR。** 这是最好的结果。

### 3.1 ⭐ 主力通路：eCFR 官方 API（免费、免密钥、JSON）

**这是美国通路的杀手锏。** 不用爬网页，直接调 API 拿结构化数据。

| 接口 | 用途 | 实测 |
| --- | --- | --- |
| `GET https://www.ecfr.gov/api/versioner/v1/titles.json` | 拿全部 50 个 Title 清单 | ✅ HTTP 200，8KB |
| `GET https://www.ecfr.gov/api/versioner/v1/structure/{日期}/title-{N}.json` | 拿某个 Title 的完整结构 | ✅ HTTP 200，747KB（Title 16） |
| `GET https://www.ecfr.gov/api/versioner/v1/ancestry/{日期}/title-{N}.json` | 拿到某个条文的完整层级路径 | ✅ 文档确认 |
| `GET https://www.ecfr.gov/api/versioner/v1/versions/title-{N}.json` | 拿某个条文的历次修订版本 | ✅ 文档确认 |
| `GET https://www.ecfr.gov/api/versioner/v1/full/{日期}/title-{N}.xml` | 拿条文完整原文（XML） | ✅ 文档确认（需压缩，否则 HTTP 406） |

**接口特点（实测 + 文档确认）**：
- **免费、无需 API Key、无需注册**
- 返回标准 **JSON / XML**
- **支持历史版本查询**（给定日期，能拿当时生效的版本）—— **这个功能对「法规变化时间线」模块是巨大加分**
- 建议设 `User-Agent`（标明来意 + 联系方式），便于对方识别
- 单次查询上限 10,000 条结果
- **高频访问可能被限速** → 必须加缓存

**实测命令示例**：
```bash
curl -A "compliance-radar/1.0" "https://www.ecfr.gov/api/versioner/v1/titles.json"
curl -A "compliance-radar/1.0" "https://www.ecfr.gov/api/versioner/v1/structure/2026-10-08/title-16.json"
```

### 3.3 美国法规编号结构（记牢，核对时用）

```
16 CFR Part 1250
│         └────── 部分号（Part）
└──────────────── 篇号（Title）
```

**完整层级**（从上到下逐级细分）：
```
Title（篇，如 16）
 └ Chapter（章，如 II）
    └ Subchapter（分章，如 B）
       └ Part（部分，如 1250）
          └ Section（条，如 1250.2）
```

**URL 规律（可以自己拼）**：
```
https://www.ecfr.gov/current/title-{篇}/part-{部分}
```
例：`https://www.ecfr.gov/current/title-16/part-1250`

### 3.5 美国通路的坑（已验证的应对）

| 坑 | 应对 |
| --- | --- |
| **eCFR 不是官方法律版**（是"权威但非官方"的编辑汇编） | 引用时**同时给 govinfo.gov 的年度官方版链接** |
| **页面被反爬拦截**（脚本访问网页会返回 "Request Access" 页） | **用 API，不要用网页路径** |
| PDF 泛滥 | 用 API 的 JSON/XML，不碰 PDF |
| 更新比欧盟频繁 | 用 `versions` 接口查修订历史，标注 `up_to_date_as_of` |

## 五、如果验证失败怎么办（退路）

**按顺序降级，别死磕：**

| 级别 | 做法 | 影响 |
| --- | --- | --- |
| **L1** | 换通路（直连 → 搜索引擎） | 无影响，只是慢一点 |
| **L2** | 换渲染方式（HTML → PDF 解析） | 增加开发量，但可行 |
| **L3** | **半自动**：AI 初筛 + 人工核验链接 | **完全可行，且符合项目定位** |
| **L4** | 收缩市场范围（美国砍掉，只做欧盟） | 范围缩小，但项目成立 |
| **L5** | 收缩品类（5 类 → 3 类） | 数据量减半 |

> **重要认知**：L3「半自动」**不是失败**。我们的产品定位本来就是「AI 辅助 + 官方来源可核验」，人工参与核验完全合理。评审看的是**结论是否可靠**，不是**全自动**。

### 🕳️ 今天踩的两个坑（务必记住，能省几小时）

#### 坑 1：CELEX 号在 SPARQL 里必须带类型标注

```sparql
# ❌ 错：返回 HTTP 200，但 bindings = 0（看起来像「这条法规不存在」）
?work cdm:resource_legal_id_celex "32025R2509" .

# ✅ 对：必须显式标明是字符串类型
?work cdm:resource_legal_id_celex "32025R2509"^^<http://www.w3.org/2001/XMLSchema#string> .
```

**为什么坑**：错的时候不报错，只是**静默返回空**。脚本会打印「未在官方数据库找到该 CELEX 号」，
让人误以为是法规号写错了，跑去改法规号 —— 方向完全错了。

#### 坑 2：欧盟法规的标题不在 work 上，挂在「语言版本」上

```sparql
# ❌ 错：work_title 永远返回 0 行
<cellar_uri> cdm:work_title ?title .

# ✅ 对：标题挂在 expression（各语言版本）上，字段名是 expression_title
?exp cdm:expression_belongs_to_work <cellar_uri> .
?exp cdm:expression_title ?title .
?exp cdm:expression_uses_language ?lang .
FILTER(CONTAINS(STR(?lang), "ENG"))    # 一条法规有 24 种语言，必须只留英文
```

**为什么坑**：第一版脚本抓出来的表格里，**16/17 条标题是空的**，
而 ELI 链接、日期全都有 —— 这种「一半有一半没有」最难发现。必须加一次体检脚本专门查空值。

### 📌 一条重要判定修正：欧盟链接「打不开」≠ 链接失效

实测 17 条欧盟链接**全部返回 HTTP 202**，正文 2035 字节，含 `awswaf` + `challenge.js`。

> **这不是链接失效，是欧盟站点的人机验证墙。真人在浏览器里点开是完全正常的。**

所以核对时要把两种状态**分开记**：

| 状态 | 含义 | 写进表格 |
| --- | --- | --- |
| `是（程序实测 200）` | 程序能直接访问，链接确实有效 | 美国 23 条 |
| `需人工浏览器验证（WAF）` | 程序被墙，但真人能打开 | 欧盟 17 条 |

**千万不要**把 WAF 拦下来当成「链接有问题」去改链接 —— 链接是对的。
