## 一、🔴 高优先级问题（必修）

### 问题 1：语料表存在重复行，实际唯一 86 条，对外宣称 88 条

**证据**：用脚本对 `data/语料核对表_完整版.csv` 复算，共 88 行，但唯一键（CELEX号 / 官方编号）只有 **86** 个。重复项为：

| 重复键 | 出现次数 | 类目 |
|---|---|---|
| `16 CFR Part 1120` | 2 | 电子电器 |
| `21 CFR Part 740` | 2 | 美妆个护 |

**根因**：`scripts/fetch_us.py` 的 `TARGETS` 列表里 `part_keys` 有重叠 —
- `1120` 同时出现在两条 target 中（第 157 行 `["1505","1120"]` 与第 173 行 `["1101",...,"1120"]`）
- `740` 同时出现在两条 target 中（第 162 行 `["700","710","720","740"]` 与第 179 行 `["701","730","740"]`）

抓取时同一个 part 被追加两次，而 `scripts/merge_corpus.py` **没有任何去重逻辑**，重复行原样进入总表、完整版、数据总览统计。

**影响**：README 与 `data/数据总览.md` 的"88 条"及各品类统计均被虚高 2 条；这也是本项目"数据准确性"定位下的明显硬伤。

**修改建议**：
1. 在 `merge_corpus.py` 的 `main()` 中，对 `allrows` 按 `(机构, 官方编号)` 去重（保留首条），并把去重数量打印出来；
2. 顺带把 `fetch_us.py` 中重叠的 `part_keys` 合并去重，避免源头重复。

```python
# merge_corpus.py：相关性筛选后、写文件前，加一段去重
seen, dedup = set(), []
for r in allrows:
    k = (r["机构"], r["CELEX号"] or r["官方编号"])
    if k in seen:
        print(f"    重复剔除：{k}")
        continue
    seen.add(k)
    dedup.append(r)
allrows = dedup
```

> 数据修复后，需同步更新 README / 数据总览中的"88 条"、"电子电器 19"、"美妆个护 7" 等数字。

### 问题 2：`骨架体检报告.txt` 数字自相矛盾（29 + 69 = 98 ≠ 88）

**证据**：`data/骨架体检报告.txt` 第 6 行：

```
总数：88 条（欧盟 29 + 美国 69）
```

**根因**：`scripts/merge_corpus.py` 第 125 行

```python
lines.append(f"总数：{len(allrows)} 条（欧盟 {len(eu)} + 美国 {len(us)}）")
```

`len(allrows)` 是**相关性筛选后**的条数（88），而 `len(eu)` / `len(us)` 是**筛选前**的原始条数（29 / 69，原始共 98）。两个口径混用，导致括号里加起来 98、外面写着 88。同时，同一脚本的控制台输出（第 102-104 行）也是打印原始条数，容易让人误以为"抓了 69 条美国数据"。

**影响**：体检报告是数据质量的"体检单"，本身数字对不上，会让复核者对整个数据管线的可靠性产生怀疑。

**修改建议**：报告统一用"筛选后"口径统计，原始条数单独说明。

```python
eu_kept = sum(1 for r in allrows if r["机构"] == "EU")
us_kept = sum(1 for r in allrows if r["机构"] == "US")
lines.append(f"总数：{len(allrows)} 条（欧盟 {eu_kept} + 美国 {us_kept}）")
lines.append(f"原始抓取：欧盟 {len(eu)} + 美国 {len(us)}，筛选剔除 {len(dropped)} 条")
```

### 问题 3：README 让用户执行不存在的 `app.py`

**证据**：`README.md` 第 223 行"运行"章节：

```bash
python app.py
```

但仓库根目录**没有 `app.py`**（已实测确认不存在），`modules/` 下也只有一个空的 `__init__.py`。README 自己在上一行也写了"代码实现正在进行中"，但给出的却是可直接复制的运行命令。

**影响**：任何人照 README 快速开始操作，第一步就报 `can't open file 'app.py'`。对参赛/评审场景尤其致命。

**修改建议**（二选一）：
- **方案 A（省事）**：把"运行"章节改为"本期尚未提供可运行的 Web 入口，数据管线见下方脚本"，并给出真实可跑的命令（`python scripts/fetch_eu.py` 等）；
- **方案 B**：若确有入口文件，补回 `app.py` 并在 README 项目结构中列出。

### 问题 4：`audit_guide.py` 硬编码仓库外部路径与固定日期

**证据**：`scripts/audit_guide.py`

```python
第 34 行：GUIDE = r"E:\浙客松天猫OPC赛道\官方法规网站查找指南.md"
第 131 行：... structure/2026-10-08/title-{title}.json
```

`GUIDE` 指向的是**仓库之外、作者本机的另一个项目目录**。任何人 clone 仓库后运行该脚本都会因找不到文件直接退出（第 155-157 行）。此外 `2026-10-08` 写死了 eCFR 数据日期。

**影响**：脚本不可复现、不可移植；还把作者本机目录结构写进了公开仓库。

（同类问题：`data/指南核对报告.md` 第 4、212 行、`docs/06-数据通路验证清单.md` 第 624 行，均残留 `E:\...` 本机绝对路径。）

**修改建议**：
- `GUIDE` 改为命令行参数或环境变量，默认值改为仓库内路径或 `None` 并给出用法提示；
- 数据日期改为从 `titles.json` 的 `meta.date` 动态获取，或作为参数传入；
- 清掉文档里的本机绝对路径。

## 二、🟡 中优先级问题（建议修）

### 问题 5：文档要求的字段规范与实现不符（缺"序号""OJ 出处"）

`docs/03-AI执行手册.md`（第 167-170 行）规定语料字段为 20 项，含 **"序号""官方链接（EUR-Lex）""OJ 出处"**；README 的 M1 输出（第 127 行）也承诺包含 **"OJ 出处"**。

但实际 `data/语料核对表_完整版.csv` 只有 **18 列**，既无"序号"，也无"OJ 出处"。

**影响**：M1 模块按 README 承诺要输出"OJ 出处"，但数据源里根本没这个字段 —— 需求与数据资产脱节。

**建议**：统一口径。要么补 `OJ 出处` 列（`fetch_eu.py` 可从 SPARQL 取 OJ 编号），要么把 README/docs 的字段描述改为与 18 列一致。

### 问题 6：`docs/06` 全篇数据量过时，与 README 打架

`docs/06-数据通路验证清单.md` 通篇是 **"40 条（欧盟 17 + 美国 23）"**（第 5、88、92-94、538、609-619 行），而 README / 数据总览 / `docs/给Codex的PRD提示词.md` 均为 **"88 条（29 + 59）"**。`data/欧盟待补清单.md` 标题也还是"欧盟 17 条"。

**影响**：同一仓库出现 40 / 88 两套数据量，评审容易质疑"到底做了多少"。

**建议**：在 docs/06 顶部加一行"⚠️ 本文为过程快照（10.14 完成时点），最终数据量以 `data/` 与 README 为准（88 条）"，或直接更新数字。`欧盟待补清单.md` 由 `make_todo_eu.py` 生成，脚本里写死了"17 条"标题，建议改为按实际条数动态生成。

### 问题 7：合并时丢失美国监管机构粒度（CPSC/FDA/FCC/FTC → 全变 US）

`data/us_regulations.csv` 的"机构"列是 **CPSC(40) / FCC(2) / FTC(8) / FDA(19)**，但 `scripts/merge_corpus.py` 的 `load()` 用 `rr["机构"] = org` 把全部覆盖成 `"US"`。

**影响**：合并后的主底表丢掉了"这条归哪个机构管"，而 M1 合规地图恰恰需要体现监管机构。

**建议**：新增一列"监管机构"（保留 CPSC/FDA/FCC/FTC），"机构"列继续用于区分 EU/US；或干脆不覆盖，另设"市场"列。

### 问题 8：依赖清单与设计说明矛盾（引入 RAG 库却声明不用 RAG）

`requirements.txt` 第 22-24 行：

```
# --- 检索（RAG） ---
numpy>=1.26.0
scikit-learn>=1.5.0
```

而 README（第 178-186 行）明确论证"**为什么不用向量检索（RAG）**"。

**影响**：自相矛盾会削弱"技术选型经过思考"的说服力。

**建议**：删除这两行未使用的依赖；若因其他原因保留（如 Gradio 间接依赖），在注释中说明。

### 问题 9：生成物中硬编码时间戳 / 条数

- `scripts/make_overview.py` 第 46 行写死 `> 生成时间：2026-10-14 18:30`；第 146 行写死 `88 条 × 18 列`。
- `scripts/audit_guide.py`、`data/指南核对报告.md` 也写死 `2026-10-14 18:15` 等时间。

**建议**：改 `datetime.now().strftime(...)`，条数用 `len(rows)` 动态计算，避免"重新生成后时间/数字还是旧的"。

### 问题 10：欧盟"官方编号"格式非标准

`scripts/fetch_eu.py` 第 279 行：

```python
"官方编号": f"{etype}{year}/{num}" if etype and year and num else celex,
```

生成结果如 `R2025/2509`、`L2009/48`，而官方标准写法是 **`Regulation (EU) 2025/2509`** / **`Directive 2009/48/EC`**。当前格式既非 CELEX、也非官方引用格式，读者容易误解。

**建议**：按类型映射前缀生成官方写法（R→`Regulation (EU) ...`、L→`Directive .../EC`），或在该列明确标注为"简化编号"。
