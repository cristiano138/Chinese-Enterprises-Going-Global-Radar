- **没有「重新检查」按钮**，没有筛选，没有让用户操作
- 首页只回答：最近一次什么时候查的、查了多少、结果是什么
- 「查看检查记录」进入只读报告页，仍然没有重新检查的入口
- 检查结果必须如实：如果最近一次检查距今太久，就显示“最近检查 3 天前，数据可能已过期”，不能假装刚查过

  - **用示例数据看看**：加载“儿童玩具 / 德国 / 亚马逊”的示例，让用户看到完整首页
  - **查看完整指引**：进入「我的 → 教程」，即《企业用户使用指引》
- 教程内容不新写，只把旧入口名改成新导航：

## 五、时效性检查：只展示结果

### 系统在做什么

现有实现是 `scripts/check_freshness.py`：

- 读取 `core/corpus.py` 里的 86 条官方链接（官方链接 + ELI 链接，去重）
- 并发 GET，记录 HTTP 状态、Last-Modified、内容哈希
- 每次核验每链接追加一行到 `data/freshness_log.jsonl`
- 最新汇总写到 `data/freshness_latest.json`

### 页面只展示

- 最近检查时间、数据截止日期
- 核验链接数、可访问数、待复核数、内容更新数
- 最近两次检查记录
- 待复核链接（网络未连通不判死链，下一次会重试）
- 检查口径说明

### 不做

- 不在页面上放“重新检查”按钮
- 不让用户选择检查范围或过滤结果
- 不把“内容哈希变化”说成“法规条文变更”
- 不把平台规则算进自动检查；平台规则仍需人工看卖家后台

### 定时

- 目标节奏：每天 09:00 / 21:00
- Windows 计划任务或 cron 均可；线上创空间没有 cron 入口时，改用 GitHub Actions 每日跑并回写仓库
- 页面只读 `freshness_latest.json`；文件不存在或过期时如实提示，不伪造

## 十、待确认

1. 第一次使用的判定：是按“没有业务条件”，还是按“还没有检查记录”？当前原型按“没有检查记录”展示教程态。
2. 最近一次检查超过多久算过期：12 小时还是 24 小时？建议 12 小时，超过就在首页显示“数据可能已过期”。
3. 待复核链接在首页显示几条：当前 2 条；如果实际有几十条网络失败，需要折叠成“N 条待复核”，避免首页被异常列表占满。
