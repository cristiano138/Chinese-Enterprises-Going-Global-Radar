# 出海合规雷达 · 路由层（M1.5）两类未支持问题

> 记录时间：2026-10-17
> 用途：实测发现 M1.5 路由层对「多品类多市场」「比较/增量合规」两类问题目前都会悄悄退化成单点查询，且不提示用户。不是 bug 修复，是功能缺口，供后续决定要不要做、做到什么程度。
> 涉及代码：`modules/m15_router.py`（`route()` / `parse_model()` / `PARSE_PROMPT`）、`modules/m1_map.py`（`query()`）、`core/corpus.py`（`search()`）

---

## 一、问题根源：槽位结构本身是单值设计

`PARSE_PROMPT`（`m15_router.py:207-229`）定义的 JSON schema：

```json
{"品类": "", "市场": "", "用户品类": "", "用户市场": "", "命中依据": ""}
```

`品类`/`市场` 是**字符串**，不是数组。词典解析 `parse_local()` 里的 `_best()`
函数（`m15_router.py:249-261`）同样是「命中最多的那个 label 胜出」的单点逻辑。
最终落到 `modules/m1_map.py:104` 的 `query(category, market)`，底层
`core/corpus.search()` 也是按单一 (品类, 市场) 组合去匹配语料——
整条链路从提示词到数据层，都是「一次问一个品类在一个市场」的设计，
不是哪一层写错了，是没有为多对多场景设计过。

---

## 二、问题一：多品类多市场输入 → 悄悄只答一个组合

### 实测输入
> 我们公司同时卖玩具、服装、电子产品、化妆品，想同时进入美国、欧盟、
> 英国、日本、韩国市场，不知道该怎么合规，能不能都说一下

### 实测结果
- `parse_model()` 返回：标准化的 `品类`/`市场` 字段**判定为空**（模型意识到
  是多值、无法填进单值枚举），但 `用户品类`/`用户市场` 老实抄下了用户说的
  全部原词（"玩具、服装、电子产品、化妆品" / "美国、欧盟、英国、日本、韩国"）。
- 模型两个标准槽位都空 → `route()` 退回词典解析 `parse_local()`。
- 词典按「命中最多的那个」硬选：`品类=纺织服装`（命中"服装"二字），
  `市场=欧盟`（命中"欧盟"二字）。
- 最终返回 `ok=True`，`route_via=本地词典解析`，给出「纺织服装 × 欧盟」
  **这一个组合**的清单。用户问的其他 4 品类 × 4 市场（共 24 种组合）
  被静默丢弃，界面上没有任何「只回答了其中一部分」的提示。

### 问题性质
不是报错、不是拒绝——是**悄悄给了一个用户没主要问的答案**，且没有任何
告知机制。用户如果不细看，会误以为「纺织服装在欧盟」就是对自己整个
问题的完整回答。

### 可能的处理方向（供后续决策，未实现）
1. **最小改动**：`route()` 检测到 `用户品类`/`用户市场` 里含多个实体
   （比如含「、」「，」分隔的多个受支持词）时，不强行单点查询，
   直接提示「检测到多个品类/市场，请逐一查询，例如先问『玩具卖欧盟』」。
2. **功能增强**：拆成多次单点查询（笛卡尔积或仅用户关心的组合），
   合并渲染成多个判定卡。工作量明显大于方向 1，且要考虑卡片数量上限
   （25 种组合全展示体验会很差）、要不要加「只列前 N 个 + 其余请单独查」。
3. 无论选哪个方向，都要先排除「模型两个标准槽位都为空」与「真的没说
   品类/市场」（现有 `no_slots` 分支）的歧义——目前这两种情况在
   `route()` 里是同一条路径，需要先用 `用户品类`/`用户市场` 是否
   非空且含多个实体来区分。

## 三、问题二：比较 / 增量合规问题 → 悄悄答成「全量」而非「增量」

### 实测输入
> 我已经在欧盟卖过洋娃娃了，去美国继续卖洋娃娃还需要做哪些合规工作

### 实测结果
- `parse_model()` 正确识别出 `品类=儿童玩具`，`市场=美国`（抓住了
  「去美国」的意图），`用户市场` 字段里保留了「欧盟、美国」两个原词，
  `命中依据` 字段也完整记录了「欧盟卖过洋娃娃、去美国继续卖洋娃娃」。
- `route()` 把这当成一次**普通的**「儿童玩具 × 美国」查询，
  `ok=True`，`route_via=模型解析`。
- 下游 `m1_map.query("儿童玩具", "美国")` 返回的是美国儿童玩具合规的
  **完整清单**，不是「相对于欧盟，美国额外要做的部分」的差异清单。
- 「已经在欧盟卖过」这个前提信息被模型抓进了 `命中依据`，但路由和
  M1 查表完全不使用这个字段做任何差异计算——它只是原样显示在
  「识别依据」里，不参与任何实际逻辑。

### 问题性质
比问题一更隐蔽：系统没有报错、没有降级标注，答案看起来完全正常，
但语义上是错的——用户问的是「增量」，拿到的是「全量」。如果用户
把列出的全部条目都当成「相对欧盟新增的要求」去执行，会多做很多
欧盟那边其实已经满足的工作（如果两地要求有重叠），这是会误导用户
实际合规动作的问题，不只是体验问题。

### 根源：数据层没有「法规等价/重叠」的概念
`core/corpus.search()` 按市场独立组织法规清单，语料里没有「法规 A
在欧盟和美国分别对应哪条、要求是否重叠」这类跨市场映射字段。没有
这个数据基础，「增量」在当前架构下**算不出来**，不是路由层能单独
解决的问题。

### 可能的处理方向（供后续决策，未实现）
1. **最小改动（文案兜底）**：路由层检测到 `命中依据`/`用户市场` 里
   出现「已经/already/继续/再」这类增量意图词，且识别到两个不同市场时，
   在结果卡片顶部加一行提示：「以下是美国市场的完整合规清单，
   不是相对欧盟的增量清单，欧盟与美国的要求如有重叠需自行核对」。
   不改变查询逻辑，只是不让用户误读。
2. **数据增强（工作量大，影响范围广）**：给语料加「同类法规跨市场
   映射」维度（例如都是"包装标识要求"但欧盟引用 X 条、美国引用 Y 条），
   路由层据此做集合差（美国要求 − 欧盟要求 ∩ 美国要求 = 新增部分）。
   这个方向会改动数据结构（见 `备忘/待补充法规清单.md` 里提到的字段
   扩展问题），建议先确认这类「同主题跨市场对应」在法规层面是否
   真的能一一对应（现实中很可能不是严格的子集/超集关系，可能需要
   领域专家介入判断，而不是单靠字符串/关键词匹配）。
3. 折中：先不做自动差异计算，但在 missing/待办（M3）环节，针对
   「用户提到已在其他市场销售」这种情况，生成一条待办项提醒用户
   「建议对照欧盟与美国同主题法规逐条核对重叠项」，把判断留给人。

## 四、两个问题的共同建议

- 两者都不是「哪里写错了」，是设计时就没覆盖这两类场景，属于
  产品范围决策，不是单纯改代码能解决的，需要先定好「要支持到什么
  程度」再动手。
- 如果近期要做，建议问题一优先于问题二：问题一只是「漏答」，
  用户容易发现；问题二是「答错但看不出来」，风险更高，但解法
  依赖的数据基础目前不具备，改动成本和不确定性都更大。
- 两个方向都建议先做「最小改动（文案兜底/提示）」，让系统至少
  对自己的局限性保持诚实（这也是项目 README 反复强调的「宁可拒绝，
  不要猜」的原则），再考虑要不要投入做真正的多对多查询或差异计算。
