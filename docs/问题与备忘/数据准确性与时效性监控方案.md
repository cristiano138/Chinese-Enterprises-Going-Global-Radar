# 出海合规雷达 · 数据准确性与时效性监控方案

> 记录时间：2026-10-17
> 用途：讨论"如何确保项目法规数据的准确性和时效性、时效性监控脚本怎么改进"的结论记录，供后续迭代参考，不入库、不进项目目录。

---

## 一、先分清两个不同的问题

- **准确性问题**：现在表里存的这条信息，是不是真的、编号对不对得上原文。这个一次性核对完基本稳定，周期性复查即可。
- **时效性问题**：这条信息会不会突然被改了，我多久能发现。这是持续性问题，得一直跑监控。

两者解决方式不同，不能用同一套机制应付。

---

## 二、现有 `scripts/check_freshness.py` 做到了什么程度

已读过代码（2026-10-16 落地的最小可行版），它监控的是**链接层**，不是**内容层**：

- 访问每条官方链接，看 HTTP 状态码（能不能打开）
- 读前 128KB 内容算 sha256 哈希，跟上一次哈希比对，哈希变了标记 `changed`

**关键限制**（代码注释里自己也承认，见 `docs/时效性监控.md` 第 33-34 行）：
"内容有更新"只是网页字节变了，**不等于法规条文真的改了**。页面加个 cookie 弹窗、改个广告位、换个页脚版权年份，哈希都会变，但跟法规内容无关。反过来，法规真改了但官方还没重新渲染页面，哈希可能暂时不变。

**结论**：现有机制的真实作用是"提醒有网页动了，该去人工看一眼"，不是"自动确认法规改了什么"。这个设计在 4 天工期下是合理且诚实的，但要清楚边界在哪，不能对外宣传成"自动检测法规变化"。

---

## 三、确保准确性：一次性核对 + 周期性复查

1. **编号对得上**：欧盟用 CELEX 号，美国用 CFR Part 号，拿官方检索工具搜一遍，确认能搜到同一份文件（对应 `docs/04-官方来源判定指南.md` 第七节的底线要求）
2. **链接能回到原文**：必须是 `eur-lex.europa.eu` 或美国监管机构官方域名，不能链接到第三方转述页、律所解读页
3. **这一步工作量大，不可能全自动**。项目表里留了"核对人""核对日期"两列手工签字字段，这是对的做法——机器只能筛出"疑似有问题"的条目，真正确认对错还得人工看一眼

---

## 四、确保时效性：三层监控，按性价比排序

### 第一层（已完成）：链接活性监控
现有脚本够用。HTTP 状态码 + 内容哈希，一天跑一次，成本很低。继续保留。

### 第二层（建议下一步做）：官方"修订记录"接口监控，取代"猜整页哈希"

这是比"整页哈希"聪明很多的做法。欧盟和美国官方都提供**结构化的"这份文件历史上改过几次、最近一次什么时候"**数据，不需要靠猜网页字节变不变：

- **欧盟**：EUR-Lex 的 SPARQL 接口（`scripts/fetch_eu.py` 已经在用）本身就能查到"最新修订日期"这种结构化字段。直接问接口"这个 CELEX 号最后修订日期是哪天"，跟表里存的日期比对，不一样就报警
- **美国**：eCFR 官方 API 同样提供 "last amended" 字段（已用 WebSearch 核实：eCFR 页面会显示 "up to date as of" 和 "last amended" 两个日期）。同样可以直接问接口要日期，不用猜

**好处**：
- 不用新增数据源，`fetch_eu.py` / `fetch_us.py` 里查询官方接口的代码已经写好，复用即可
- 判定依据从"猜哈希"变成"问官方权威字段"，误报率大幅下降（哈希监控现在很容易因页面无关改动误报，官方修订日期字段不会无缘无故变）
- 跟第一层链接活性监控不冲突，可以并存——链接层继续用哈希兜底"网页是不是整体消失或大改了"，修订日期层专门盯"内容真的改了没"

**伪代码思路**（不是真实代码，供后续实现参考）：

```python
def check_official_revision_date(celex_or_cfr_number, market):
    """问官方结构化接口要最新修订日期，而不是猜网页哈希"""
    if market == "EU":
        # 复用 scripts/fetch_eu.py 里已经写好的 SPARQL 查询逻辑
        latest_date = query_eurlex_sparql(celex_or_cfr_number)
    else:
        # 复用 scripts/fetch_us.py 里已经写好的 eCFR API 调用
        latest_date = query_ecfr_api(celex_or_cfr_number)

    stored_date = corpus_row["最新修订日期"]
    if latest_date != stored_date:
        return {"flag": "revision_date_mismatch", "official": latest_date, "stored": stored_date}
```

### 第三层（暂不做）：全文级 diff
定期抓全文存起来，逐段比对具体哪里改了。工作量大（PDF 解析、存储、版权边界），项目文档已明确"本期不做"，这个判断是对的，现阶段不建议加。

## 五、下一步建议顺序

1. 保留现有链接活性监控（第一层），不用动
2. 优先实现"官方修订日期比对"（第二层）——复用已有抓取代码，投入产出比最高，能把"内容有更新"提示从"大概率误报"变成"真的值得人工复核"
3. 全文级 diff（第三层）继续放在路线图里，不动

## 六、合并版 / eCFR 相关的背景结论（供交叉参考）

与本次讨论相关的背景结论，一并记录：

- 欧盟合并版（Consolidated text）和美国 eCFR，本质上是同一类东西：官方出品、但官方自己声明"不具法律效力"，只是方便查阅的编辑性汇编
- 真正权威文本：欧盟是《官方公报》（Official Journal）电子版；美国是《联邦公报》（Federal Register）上的修订文件 + 官方年度 CFR 版本
- 法规生效时间由修订文件自己写的生效日期决定，跟合并版/eCFR 更新与否无关；合并版/eCFR 都是"事后补拼"，滞后于法律生效（欧盟约 2-3 周，美国约 2 个工作日内）
- 这正是项目 README 里"美国条目生效日期实为 eCFR 收录日，非真实生效日"这条已知限制的根源——eCFR 标的日期本质是"编入汇编的时间"，不是"法律生效时间"
