# 法规召回目录树说明

版本：2026-10-18 ｜ 入口：`scripts/build_recall_tree.py`、`core/recall.py`

## 1. 目的

路由 LLM 选定法规后，检索 LLM 需要在每部法规的“目录树”里选具体切片。
`units` 表是扁平的（PK `document_id, ordinal`），没有父子关系、路径、分块或
重要性字段，不能直接给检索层使用。

本层把 `units` 整理成**可重建的派生目录树**，写入同一数据库的四张表，不改
`laws / documents / law_documents / units`：

| 表 | 用途 |
|---|---|
| `recall_law_docs` | 每法选中的 canonical 文档、选择原因、叶子数/字符数、fallback |
| `recall_nodes` | 树节点：法规根 / 条款 / 附件 / subpart 容器 / 分块叶子 |
| `recall_nodes_fts` | FTS5 索引（`heading` + `body`），供确定性粗召回 |
| `recall_build_meta` | tree_version、chunker_version、max_chars、构建时间、校验状态 |

## 2. 已确认口径

1. **EU 优先 `eu_consolidated`（现行合并文本）**，结构不完整时退回 `primary`；
   US 用 `primary`（eCFR）。
2. **v1 只建现行法规树**：修正案、勘误、FR 规则发布、bulk fallback、annual
   reference、cited source reference 都不进树。
3. **分块上限 6,000 字符**；语义锚点优先，最后才硬切。
4. **US eCFR 的 subpart 只当容器**：它的 body 100% 包含其下 section，复制会
   造成 630 万字符重复和重复 FTS 命中。
5. **THIN（2–4 个叶子单元）仍建结构化节点**，标 `thin`；只有零结构化单元才
   用全文兜底。当前无零结构化法规。

### canonical 选择规则

叶子计数口径：EU = `article + annex`；US = `section + appendix`；`subpart`
只算容器。

```text
US                                   -> primary，reason=us_primary
EU 无 consolidated                    -> primary，reason=no_consolidated
consolidated.full_text < 500          -> primary，reason=consolidated_no_full_text
consolidated.leaf_units < 5           -> primary，reason=consolidated_below_min_units
consolidated.leaf_units < ceil(0.8 * primary.leaf_units)
                                      -> primary，reason=consolidated_low_coverage
其余                                  -> consolidated，reason=consolidated
```

当前 86 条法规的结果：`consolidated=22`、`consolidated_no_full_text=3`、
`consolidated_below_min_units=1`、`no_consolidated=3`、`us_primary=57`。

## 3. 树形结构

```
法规根 (node_type=law, depth=0)
├─ EU: article / annex / appendix (depth=1)
│    └─ chunk (depth=2；仅超长条款/附件)
└─ US: subpart 容器 (depth=1)
     ├─ section / appendix (depth=2)
     │    └─ chunk (depth=3)
     └─ [Reserved] subpart 短叶子 (is_substantive=0)
```

- `path` 示例：`EU:32008R1272 > ANNEX VI > [part 2/219]`；
  `US:47:15 > Subpart A — General > § 15.1 — Scope of this part.`
- `node_id` 稳定、可读：`rc|<law_id>|root` / `u<ordinal>` / `u<ordinal>|c<i>`；
  不依赖文档版本。外部引用请同时保存 `tree_version`。
- 容器 `body=NULL`；只有叶子/分块有正文。`is_leaf`、`is_substantive`、
  `importance`（`high` / `normal` / `context` / `navigation`）供检索层过滤。

## 4. Heading 质量与来源

不是所有 heading 都“自带”：

| 来源 | heading 来源 | 质量 |
|---|---|---|
| US eCFR section/subpart | 原生 XML `<HEAD>` | 抽样 300/300 与原生一致 |
| EU article/annex | `heading` 列是 `backfill_units_heading.py` 从 body 第 1/2 行推导；标题文本在源 HTML 里原生存在 | 抽样 300/300 与非纯编号 heading 的原生 `eli-title` / `oj-ti-art` 一致 |
| `pdf_page` / `n` / `auth` / `source` / `text_block` | “Page N” 或空 | 噪音，不进树 |

当前构建：

- `label_only=6`：全部是确实没有标题的短条款（`31994L0011` Article 3/4/5、
  `32001L0095` Article 7/11/16）；不编造标题。
- `title_enriched=301`：从 body 第二行或源 fragment 补出标题。
  - 关键补充：EU Formex/旧式 XML 的 `<STI.ART>` 标题（如 32005R0396 的
    “Subject matter”“Scope”“Definitions”），此前正则没覆盖。
- `reserved=28`：US `[Reserved]` 条款/subpart，已标 `is_substantive=0`，
  检索时应过滤。
- 3 条 `▼M` / `►M` 修订标记已在归一化时清掉。

纯编号节点仍保留 `label`，候选召回时通过 `snippet`（首 400 + 尾 200 字符）
让检索 LLM 依靠正文判断；预注入目录时也应带短预览。

## 5. 分块

常量：`MAX=6000`、`MIN_PIECE=400`、`HARD_OVERLAP=min(200, MAX//20)`。

策略顺序（按法规/类型）：

```text
CLP Annex VI (EU:32008R1272)  -> clp_index, eu_para, block, hard
REACH Annex XVII (EU:32006R1907) -> annex_entry, eu_para, block, hard
annex                          -> annex_entry, clp_index, eu_para, eu_heading, block, hard
section                        -> us_para_top, us_para_numbered, us_heading, block, hard
article                        -> eu_para, eu_heading, block, hard
appendix                       -> us_para_top, us_para_numbered, block, hard
THIN / full-text fallback      -> eu_para, us_para_top, us_para_numbered, heading, block, hard
```

- 每个锚点之前的文本保留为 `intro` 块（如 annex 的适用范围），不丢。
- 锚点块仍超限时递归用下一优先级；最终 fallback 复用 Loong Lab
  `chunk_service.chunk_text()` 的段落/句子/逗号切分 + 尾部重叠算法，并补了
  最终 `max_chars` 硬上限保护。
- 如果最终只有 1 块，保留为整段叶子，不建“单子节点容器”。

当前 1,418 个分块，策略分布：
`us_para_top=513`、`annex_entry=493`、`clp_index=253`、`eu_para=123`、
`block=32`、`eu_heading=4`；**没有 hard_window 兜底**。

## 6. FTS 与中文限制

- `recall_nodes_fts` 索引 `heading` + `body`，`tokenize='unicode61 remove_diacritics 0'`。
- 顶层检索用 `bm25(fts, 0, 0, 5.0, 1.0)`（heading 权重 5、body 权重 1），
  每个法规取 top N。
- **中文 query 不能直接命中英文正文**（实测“邻苯二甲酸酯”对“phthalate”无结果）。
  路由层必须输出英文 facet 关键词；`candidate_nodes` 对无 ASCII token 的输入
  走确定性回退（该法 importance/depth 排序的叶子），不会抛错。
- 多词输入先构造整句短语再 OR 逐词（复用参考项目“短语优先 + OR 召回”思路）；
  `CE marking` 在 Toy Directive 内能命中 Article 16/17。
- `remove_diacritics 0` 是为了避免 `ce` 误命中其他语言的 `če`；英文重音词会
  按原字符匹配。

## 7. CLI

```bash
# 冒烟（不写库）
python scripts/build_recall_tree.py --dry-run --limit 5

# 全量演练（不写库、不建表、不写报告）
python scripts/build_recall_tree.py --dry-run

# 正式写库（默认全量 86 法；--limit 只允许与 --dry-run 同用）
python scripts/build_recall_tree.py --backup

# 校验已有树
python scripts/build_recall_tree.py --check

# 对副本操作（推荐先用副本验证）
python scripts/build_recall_tree.py --db ../sqlite/copy.sqlite3 --backup
```

- `--max-chars N`：默认 6,000，最小 500。
- `--report PATH`：默认 `data/recall_tree_report.json`。
- `--no-quick-check`：紧急跳过写前 `PRAGMA quick_check`。
- 退出码：0 成功；1 校验失败；2 用法/DB/schema 错误。
- 写库是单事务：`DROP/CREATE` 派生表 → 先插根再插子节点 → 重建 FTS →
  写 meta → DB 校验 → commit → `wal_checkpoint(TRUNCATE)`。失败自动回滚。

## 8. 只读访问层 `core/recall.py`

```python
from core import recall

recall.tree_version()                 # 当前树版本
recall.law_catalog(as_numbered=True)  # 紧凑法规目录，带 1-based ref
recall.load_tree(law_ids, include_body=False)  # dict[law_id] -> list[node]
recall.candidate_nodes(law_ids, ["phthalate"], limit_per_law=20)
recall.get_nodes(node_ids)            # 取全文
recall.resolve_refs(refs, candidates) # 严格校验 LLM 返回的 ref
```

- 只读 URI `file:<db>?mode=ro` + `PRAGMA query_only=ON`。
- `candidate_nodes` 返回 `ref / node_id / law_id / heading / path / snippet /
  score`；`snippet` 是 FTS 命中片段，无命中时用首 400 + 尾 200。
- **编号契约**：路由 LLM 返回 `law_refs`，检索 LLM 返回 `{"ref": int}`；
  代码用 `resolve_refs`/`law_catalog` 做范围校验，越界/非整数丢弃并计数。
  模型不返回自由文本 law_id 或 node_id。

## 8.5 两层召回流程 `modules/recall_flow.py`

```text
用户业务描述
  -> route_laws():
       确定性预筛目录（M1.5 词典 + 横切标题提示）
       -> 路由 LLM 返回 law_refs/facets/catalog_gaps
       -> recall.resolve_refs() 严格校验
  -> retrieve():
       recall.candidate_nodes() 生成编号候选
       -> 检索 LLM 返回 selected ref + facet + coverage/gaps
       -> recall.resolve_refs() 校验 -> recall.get_nodes() 取全文
  -> 返回 route / retrieval / citation_map / latency_ms
```

### 参数与延迟

| 项 | 值 |
|---|---|
| 路由超时 / 检索超时 | 3.5s / 3.5s（`thinking=False`） |
| max_tokens | 路由 360 / 检索 420 |
| 路由目录 | 先用 M1.5 词典 + 横切标题提示预筛；识别不到品类或点名法规时用全量 86 条 |
| 每法候选 | 法规 ≤8 时 6 条；≤14 时 4 条；更多时 3 条 |
| 最多法规 / 切片 | 20 / 20 |
| 模型缓存 | `use_cache=False`（原文不落盘）；内存只缓存成功结果，key 是 sha256 |

实测（DeepSeek Flash，`thinking=False`）：

- 简单查询「儿童玩具出口欧盟需要符合哪些标签和化学要求」：约 **3.5s**，6 法，
  14 个切片，coverage=sufficient。
- 复杂查询「带蓝牙的毛绒玩具同时卖欧盟和美国，对比化学安全和标签要求」：
  约 **3.2–5.0s**，20 法，16–20 个切片，coverage=partial，gaps 如实列出
  （如 FCC/US 无线电、EU 玩具附件 II 具体限值未在候选中）。

### 确定性兜底

- 模型不可用/超时/JSON 解析失败：路由走 `m15_router.parse_local` 的品类×市场
  过滤，检索走每法前 2 条候选；`coverage=partial` 并写明原因。
- 失败结果不缓存（网络抖动不能让同一输入永远降级）；成功结果才进内存缓存。
- 源数据的「类目」是单标签：REACH/CLP 被标到纺织服装。预筛时会把标题含
  `chemical/substance/classification/labelling/...` 的法规额外带进目录，
  避免化学/标签问题看不到 REACH/CLP。

### CLI、自检与评测

```bash
python modules/recall_flow.py "带蓝牙的毛绒玩具同时卖欧盟和美国，对比化学安全和标签要求"
python scripts/selftest_recall_flow.py     # 33 项桩注入自检，不联网
python scripts/eval_recall_flow.py         # golden set 评测（模型路径，约 30–40s）
python scripts/eval_recall_flow.py --no-llm  # 确定性兜底基线
```

Golden set：`data/recall_golden.json`（8 条 query → expected_laws），评测报告
`data/recall_eval_report.json`。指标：route recall（路由层选中期望法规的比例）、
slice recall（最终切片覆盖期望法规的比例）、extra laws、invalid refs、coverage、
p50/p95 延迟。

当前基线（DeepSeek Flash，`thinking=False`，2026-10-18）：

| 指标 | 值 |
|---|---:|
| 平均 route recall | **100%**（8/8 query 全部命中期望法规） |
| 平均 slice recall | **93%** |
| 无效 ref | 0 |
| 失败 | 0 |
| 延迟 p50 / p95 / max | **3.6s / 4.1s / 4.1s** |

`bt_toy_compare` 的 slice recall 为 61%：路由层已选全期望法规，但检索层受
每法 3 条候选和最多 24 条切片的预算限制，没有覆盖到所有期望法条；gaps 会
如实列出。`cup_eu_us` 为 86%。下一步可以按评测结果调候选预算或加 facet。

## 9. 与参考项目（Loong Lab）的复用关系

直接复用/借鉴：

- `chunk_service.chunk_text()`：段落/句子/逗号切分 + 尾部重叠（vendored，
  保留出处；不跨仓库 import，因为原模块级依赖 `jieba`）。
- `_make_chunk_preview`：首 400 + 尾 200 的预览口径。
- `_build_fts5_query`：停用词 + 逐词引号 + OR 的查询构造思路（英文侧不引入 jieba）。
- `project_match_llm`：严格 ref 校验（整数、范围、越界丢弃、去重）。
- `verify_chunks` 的不变量思路：父节点存在、无重复 ID、FTS 行数一致、叶子范围有效。

没有照搬：

- 参考项目的单检索 Agent + `list_sections/search/get_section/get_resources`
  工具循环。我们的候选集小、5 秒预算紧，改成确定性预执行：
  `load_tree` 预注入目录、`candidate_nodes` 预跑 FTS、`get_nodes` 取全文。
  以后若法规量或多跳需求上来，再加有界扩展，而不是自由工具循环。
- 参考项目的 3,000 字符上限和中文标准标题检测；我们的法规正文更密，用户已定
  6,000。

## 11. 已知边界与下一步

- **EU chapter 层未建**：v1 是 law → article/annex；需要时再加 chapter/section 嵌套。
- **US FR § 级切分未做**：修正案不进树；未来若召回修正案，用 `machine_xml`
  的 `<PART>/<SECTION>` 结构化切分。
- **annex 表格**：CLP/REACH 有专用锚点；MRL 等纯表格 annex 走段落/空行切分，
  建议后续抽查前 10 大 annex。
- **中文 FTS**：本期不做向量检索；路由层必须给英文 facet。
- **新法规/变更材料落库**：已补链路 `core/law_intake.py` →
  `scripts/ingest_law_material.py`（manifest → documents/law_documents/units）→
  `scripts/refresh_recall_pipeline.py`（状态/task/重建）→
  `scripts/build_recall_tree.py`，详见 `docs/法规材料落库链路.md`。
  仓库仍没有自动 EU/US 全文抓取 + units 解析器；抓全文/切 units 由 agent 或
  外部解析器完成，manifest 是稳定接口。
- **THIN 法规**：14 条保留 2–4 个结构化节点；如果后续发现颗粒度不够，再决定
  是否合并或补全文。
