## 一、P0（会让产品说假话或让门禁失效）

### P0-1 发布门禁在最新提交上是失败的

`core/llm.chat()` 新增 `thinking` 参数后，`scripts/selftest_m15.py` 的两个桩函数
没跟着改，整条门禁直接 TypeError 崩溃：

```
TypeError: stub.<locals>.fake_chat() got an unexpected keyword argument 'thinking'
=== RELEASE GATE ===
失败数：1
FAIL: scripts/selftest_m15.py
```

第二处更隐蔽：`【7】硬超时` 那组的 `_slow_api()` 也是旧签名。它被
`TypeError` 打断后，测试**恰好**也看到「返回失败」，于是「超时降级」这条断言
看起来是通过的 —— 实际上是**假阳性**（把类型错误当成了超时）。只改第一处的话，
门禁会变绿，但超时链路其实从没被真正验证过。

**影响**：M1.5 模型路径的全部 30 项断言在最新提交上等于没跑；任何依赖
`selftest_all.py` 做发布拦截的流程都失效。

**修复**：两个桩函数补齐 `thinking` 形参；并新增一条断言
`thinking is False`，把「路由层关思考模式」这个新设计意图也钉进测试。

### P0-2 时效性监控漏检 29 条欧盟链接（第二次报告）

`scripts/check_freshness.py` 的 `collect_urls()` 读的列名是 `ELI链接`，
而底表的真实列名是 `ELI标识`。实测：

```
collect_urls() -> 86 条
底表实际应有  -> 115 条（官方链接 86 + ELI 标识 29）
```

**影响**：29 条 ELI 永久标识**从未被核验过**，但页脚照常显示「86/86 可访问」。
对欧盟法规来说 ELI 是「编号永不变」的那条链接，恰恰最该被监控。
「覆盖率 100%」这句话是假的。

这个 bug 上一轮（`0fe2215`）就报过并给了 patch，本轮确认**未合入**
（该文件与基线完全一致）。

**修复**：抽出 `URL_FIELDS = ("官方链接", "ELI标识")` 常量，并加
`audit_url_fields()` 口径自检 —— 扫描语料中「出现过 http 取值却没被
URL_FIELDS 覆盖」的列并告警。以后新增链接列忘了登记，会立刻被点名。
修复后实测收集 115 条（ELI 29 / EUR-Lex 29 / eCFR 57）。

### P0-3 M5/M6/M7 三个新页签没有免责声明，也没有顶部元数据

`render_m5 / render_m6 / render_m7` 只渲染内容，没有走
`_header_block()` 和 `_footer_block()`。实测原版 50 项冒烟中有 **19 项失败**，
失败原因全部是「缺免责声明」。

**影响**：
- 违反项目红灯「免责声明固定输出」——用户在区域对比页拿到的结论不带
  「不构成法律意见」；
- 违反 PRD D3「所有查询结果顶部显示查询条件/查询日期/快照版本/数据截止时间」——
  这三页无法自证数据是哪一版。

这条特别值得注意：**它是因为新功能另起炉灶、没复用老外壳造成的**。三个模块
各自实现渲染，自然就漏了公共约束。

**修复**：三个模块的 `query()` 返回值补 `header`；三个 `render_*` 补
`_header_block()` / `_footer_block()`；失败分支也带 header（和 M1–M4 一致）。
另新增 `scripts/selftest_ui_contract.py` 专门守这一层，并已挂进 `selftest_all.py`。

## 二、P1（功能可用但结论/溯源不可靠）

### P1-1 M2 / M3 的 ELI 永久标识链接被静默丢掉

`app_main._link_list()` 只读 `r.get("ELI链接")`。但这个键**只有 M1 的记录有**
（`m1_map` 把 `ELI标识` 映射成了 `ELI链接`）；M2 事件和 M3 动作里根本没有
这个键，ELI 藏在 `全部官方链接` 列表里。

实测：M2 渲染结果不含 `data.europa.eu`，M3 同样；而 M1 正常。

**影响**：主链接还在，所以不算破红线，但欧盟条目少了「编号永不变」的兜底入口。
用户点旧链接失效时就没有第二选择。

**修复**：`_link_list` 增加回退——从 `全部官方链接` 里找 `data.europa.eu/eli`。

### P1-2 M1 页签把有数据的 M2/M3/M4 显示成「空」（第二次报告）

`snapshot.header()` 的形参默认值仍是 `MODULE_EMPTY`，而 `m1_map.query()`
只传 `m1_status`。于是 M1 页签顶栏显示「变化时间线·空　合规待办·空」，但这两个
模块其实根本没跑。

**影响**：状态徽章在撒谎。用户会以为「时间线没有数据」，而实际是「这次没查」。

**修复**：默认值改为 `None`，**没传的模块不出现在顶栏**（不列 = 未查询，而不是
标成空）；新增 `MODULE_NA` 供「本应参与但未跑」的显式场景；模块名与状态中文名
收敛到 `snapshot.MODULE_NAMES` / `MODULE_CN` 唯一出口，UI 层不再自己维护一份。
`header()` 另加 `modules=` 参数，供 M5/M6/M7 自报状态。

### P1-3 M7 的「需确认」永远是 0（假的统计数字）

```python
def _task_status(action):
    if action.get("待确认") or action.get("条件待确认"):
        return "需确认"
```

这两个键在动作字典里**不存在**：`待确认` 是 m3 结果的**顶层列表**；
`条件待确认` 是导出 CSV 时按「动作来源」临时算出来的字符串。实测 26 项动作里
「需确认」0 项，页面上的「需确认 0 · 身份或条件待核」这张卡片看着像
「已核对，无待确认事项」，实际是根本没算过。

**修复**：不做「假装修好了」。删掉死分支，单项状态只保留规则算得出的
`优先处理 / 待执行`；「需确认」继续走区域级 `待确认` 列表（那是有真实来源的
清单）。代码里写明为什么现在不造这个字段，以及等 PRD F2 的 `条件待确认`
入库后再恢复。

### P1-4 「原文摘录」标注失实：把 AI 摘要当成了条文原文

`core/actions.py` 新增了 `证据摘录 = _seg0(row)`，而 `_seg0` 取的是
**备注第一段 —— 一句话中文说明，AI 预生成、已固化进 CSV**。但 UI 把它标成
「④ 原文摘录」，导出 CSV 又把它填进「来源条款」列。实测样例：

```
证据摘录: '要求通用消费品安全，卖家须确保无风险并履行追溯义务'
```

这不是任何官方条文的原文。PRD 明确要求「原文摘录可附审核后的中文解释，
**英文原文保持可见**」——原版里英文原文根本没出现，只有这条中文摘要，
还被标成「原文摘录」。

**影响**：这是合规工具最不该出的错。用户会以为自己在看条文原文。

**修复**：
- UI 的 ④ 拆成两行：先给**官方英文标题**（来自底表 `_raw`，可核验），
  再明确标注「中文要点（AI 预生成，非条文原文）」；
- CSV 的「来源条款」列填摘要时必须带来源前缀；
- 无摘要时回退到原来的「（以官方原文为准 —— 见官方链接）」，不编造。

## 四、性能：先说结论 —— 查询不是瓶颈

拆解冷启动（每行独立进程，含解释器约 30~60ms 固定开销）：

| 阶段 | 耗时 |
|---|---|
| import core（纯标准库） | 108 ms |
| + 7 个业务模块 | 287 ms |
| **+ gradio** | **3833 ms** |
| import app_main | 3868 ms |
| + build_ui()（构建 8 个页签） | 4146 ms |

**gradio 导入独占 3.5 秒，占冷启动 92%**，属框架固有开销，本项目不可控。
`build_ui()` 只占 278ms，可以接受。

查询侧实测（优化前 → 优化后）：

| 指标 | 优化前 | 优化后 | 变化 |
|---|---|---|---|
| 事件抽取 3 轮（86 行 × 3） | 2.4 ms | 1.5 ms | 1.60x |
| M3 待办单次 | 0.2 ms | 0.2 ms | 持平 |
| M2 时间线单次 | 0.2 ms | 0.2 ms | 持平 |

**必须如实说：这些微优化的绝对收益是毫秒级，对终端用户没有可感知差别。**
它们的价值在别处——批量跑 `scripts/*` 数据管线时能省时间，也让「语料改了
必须重启进程」这个坑消失。我不会把 1.6x 包装成「大幅提速」。

本轮落地的 3 项（均为上一轮报过、未合入）：
1. `core/dates.py` 事件抽取加**内容指纹缓存**（sha256 取 20 位，上限 512）。
   指纹**含 `备注／问题`**——日期线索全在备注里，漏了它就会在备注更新后继续
   用旧事件。返回值统一 copy，防调用方就地改污染缓存。
2. `core/actions.py` 事件只抽一次，`_deadline`/`urgency` 复用之（原先同一行抽 3 次）。
3. `core/corpus.py` 缓存改**按 mtime 失效**：改完底表立刻生效，不用重启。

顺带删掉 `dates.py` 尾部的无效分支（`if not include_upcoming: return events` 后接
`return events`，两分支同值，参数形同虚设）。
