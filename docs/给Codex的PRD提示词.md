## 方式一：简版（复制这一段即可）

```
你是资深产品经理。请为下面这个参赛项目写一份 PRD（产品需求文档），输出为 Markdown。

【项目背景】

【核心技术约束（必须在 PRD 中体现）】
1. LLM 只做「理解、归类、摘要、翻译」；抓取、URL 校验、引用对齐、缓存去重由确定性代码完成
2. 「引用对齐」是不可砍的底线：每条输出必须回挂官方原文链接，没有链接的内容一律不输出
3. 产品必须固定输出免责声明：「本清单仅供参考，不构成法律意见，请由专业人员复核」
4. 数据来源仅限官方公开渠道（欧盟 EUR-Lex 官方 SPARQL 接口、美国 eCFR 官方 API），不采集个人信息

【本期范围（已锁定，数据已就位）】
市场：2 个（欧盟、美国）
类目：5 个（儿童玩具、电子电器、纺织服装、美妆个护、食品接触材料）+ 通用法规

不做：更多市场、订阅推送、用户账号系统、付费功能

【分层保命原则（重要）】
- 演示主流程固定跑「儿童玩具 × 欧盟」这一条线（数据最全、案例最典型）
- 其余市场与类目作为「数据广度」展示，不作为主流程
- 若 10.16 日终主流程未跑通，立刻砍到 1 个市场 × 2 个类目并锁定

【四个功能模块】
M1 合规地图：输入类目+市场 → 输出适用法规清单，每条含法规中文名、官方编号、官方链接、生效日期、来源类型
M2 变化时间线：按「生效日期」列排序，输出相关的法规变化条目，含摘要、影响说明、生效日期、官方链接
M3 待办清单：把法规语言翻译成卖家可执行动作（如「需 CE 标识」「须指定欧盟境内授权代表」），每项标注来源条款链接，可导出
M4 对照演示：同一问题，通用大模型直答 vs 本工具并排对比，展示幻觉差异与来源可核验性（路演核心卖点）

【请输出以下内容】
1. 产品目标与成功指标（可量化，如「来源可核验率 ≥95%」）
2. 目标用户画像（含用户痛点四连：法规分散各国官网、语言专业难懂、更新频繁跟不上、通用大模型直答易幻觉）
3. 用户使用流程（从进入页面到拿到清单，分步骤）
4. M1–M4 四个模块的功能需求：每个模块写清「输入 / 处理逻辑 / 输出字段 / 边界与异常处理」
5. 数据字段定义（严格对齐这 18 列，不得自创字段名：类目、机构、法规中文名、官方标题（英文）、官方编号、CELEX号、ELI标识、官方链接、来源类型、生效日期、最新修订日期、链接可打开、编号核对、是否官方来源、核对状态、核对人、核对日期、备注／问题）
6. 界面草图描述（文字描述即可，说明每屏放什么）
7. 异常场景处理（输入无关类目、不支持的市场、来源链接失效，分别怎么提示）
8. 非功能需求（性能、部署环境、魔搭创空间兼容性）
9. 本期不做清单（明确写出哪些功能不做，防止范围蔓延）
10. 扩展路径（单列一节：本期 2 市场如何扩到日韩英加等市场，说明「换市场 = 换一个官方数据接口」，论证方法论可复制）

【输出要求】
- Markdown 格式，中文撰写，技术术语后用括号附英文
- 语气务实，不要营销腔
- 每个功能必须能落到「谁看一眼就知道怎么写代码」的程度
- 不要写测试计划、不要写营销方案、不要写财务预测
```

## 方式二：完整版（更保险，含真实案例）

如果简版输出太笼统，用这一版 —— 它多给了 Codex **真实案例 + 数据现状**，能显著提升具体度：

```
你是资深产品经理，擅长在极短工期下做「范围收窄、可落地」的产品定义。

请为下面这个参赛项目撰写 PRD v1.0，输出 Markdown，中文。

═══════════════════════════════
一、项目背景
═══════════════════════════════
项目名：出海合规雷达 ComplianceRadar
赛事：浙江大学 × 天猫校园「AI+X 破界黑客松」· 天猫校园 OPC 产业孵化赛道
截止：2026-10-18 12:00 提交（今天 10-14，只剩 4 天）
团队 3 人：詹（产品负责人/统筹/说明材料）、李（技术负责人/开发/部署）、张（数据与评测/法规核对）

痛点来源：中小跨境卖家要把商品卖到海外，必须先搞清「我这个类目要遵守哪些法规」。
现状是：法规分散在各国官网（欧盟查 EUR-Lex、美国要分别查 FDA/FCC/CPSC）、
全是英文和法律术语看不懂、法规还经常改（卖家跟不上）、
直接问通用大模型又容易编造条款号 —— 而答错法规的代价是货物被扣、罚款、下架。

产品定位：输入「商品类目 + 目标市场」→ 输出①适用法规清单 ②近期法规变化 ③可执行待办清单，
且**每条结论都附可核验的官方来源链接**。

═══════════════════════════════
二、必须遵守的技术约束
═══════════════════════════════
1. 分工原则：LLM 只负责「理解、归类、摘要、翻译」；抓取、URL 有效性校验、引用对齐、
   缓存去重全部由确定性代码完成。（原因：LLM 不可靠，凡是要「准确」的环节不能交给它）
2. 引用对齐是产品命根子：每条输出必须回挂官方原文链接；拿不到官方链接的内容，
   宁可不输出。这条功能不可因工期紧张被砍。
3. 固定输出免责声明：「本清单仅供参考，不构成法律意见，请由专业人员复核」。
4. 数据仅用官方公开渠道（欧盟 EUR-Lex 官方 SPARQL 接口、美国 eCFR 官方 API），
   不采集任何个人信息。

═══════════════════════════════
三、本期范围（已锁定；数据已完成，不是待做）
═══════════════════════════════
✅ 做：2 个市场（欧盟、美国）；5 个类目（儿童玩具、电子电器、纺织服装、美妆个护、
       食品接触材料）+ 通用法规
✅ 数据现状（已完成，可直接用）：
   - 欧盟 29 条（来源：EUR-Lex 官方 SPARQL 接口）
   - 美国 59 条（来源：eCFR 官方 API）
   - 合计 88 条，每条含：法规中文名、官方标题（英文）、官方编号、官方链接、生效日期、来源类型
   - 全部链接已程序验证（欧盟部分需人工浏览器确认，因官方站点有人机验证墙）
❌ 不做：更多市场/类目、多语言、订阅推送、用户注册登录、付费、移动端 App、后台管理
理由：只剩 4 天，范围一扩张就会全线崩盘。

═══════════════════════════════
四、分层保命原则（务必写进 PRD 的范围章节）
═══════════════════════════════
1. 演示主流程固定为「儿童玩具 × 欧盟」—— 这一条线数据最全、案例最典型，必须跑通。
2. 其余市场与类目作为「数据广度」展示，不占用主流程工期。
3. 降级规则：若 10.16 日终主流程仍未跑通，立刻砍到 1 市场 × 2 类目（儿童玩具、电子电器）并锁定。
4. M1 不可砍 —— 它是整个产品的地基。

═══════════════════════════════
五、四个功能模块（M1–M4）
═══════════════════════════════
M1 合规地图
  输入：商品类目（下拉选择）+ 目标市场（下拉选择：欧盟 / 美国）
  输出：适用法规清单。每条包含：法规中文名、官方标题（英文）、官方编号
        （如 Regulation (EU) 2023/988 或 16 CFR Part 1250）、CELEX 号（欧盟独有）、
        官方链接、来源类型、生效日期

  输出：该「类目×市场」相关的法规变化条目，按生效日期排序

  ① 本工具附官方链接可当场点开核对 ② 通用大模型可能引用已废止/过时的法规

═══════════════════════════════
六、真实案例（请把这个例子写进 PRD 的用户场景部分）
═══════════════════════════════
场景：某卖家做儿童玩具，出口欧盟。
事实：欧盟已于 2025-11-26 通过新《玩具安全条例》Regulation (EU) 2025/2509，
      2026-01-01 生效，2030-08-01 起全面取代沿用十余年的 Directive 2009/48/EC（玩具安全指令）。
      （此案例已核实并收录进我们的数据底表，两条法规都在表内。）
问题：通用大模型的训练数据里仍是旧指令，直接问它多半会回答已过时的 2009/48/EC，
      且不给来源链接 —— 卖家照着做就会用错标准。
产品价值：本工具能指出「现行法规已是 2025/2509，旧指令有过渡期安排」，并附上官方原文链接。
说明：此案例请设为 M4 对照演示的默认示例。

另一个可用的反面案例（体现 AI 会编造）：
  我们实测中，AI 曾给出一个不存在的法规编号「32015R1000」，经官方接口核查确认不存在。
  这正好用于 M4 演示「通用大模型会编造编号」这一点。

═══════════════════════════════

═══════════════════════════════
类目 / 机构 / 法规中文名 / 官方标题（英文）/ 官方编号 / CELEX号 / ELI标识 /
官方链接 / 来源类型 / 生效日期 / 最新修订日期 / 链接可打开 /
编号核对 / 是否官方来源 / 核对状态 / 核对人 / 核对日期 / 备注／问题

字段说明：
- 「机构」取值：EU（欧盟）/ US（美国）
- 「来源类型」取值：官方原文（OJ）、官方整合版、官方摘要、非官方（第三方）、待确认

- 「最新修订日期」目前仅美国 CFR 条目有值
- 「核对人」「核对日期」由人工点开链接后填写，是人工签核字段

═══════════════════════════════
八、请输出的章节
═══════════════════════════════
```

## 使用建议

| 情况 | 用哪版 |
|---|---|
| 就想快速拿一版看看 | **简版** |
| 简版输出太泛、李说"没法照这个写代码" | **完整版** |
| 两个都试，让 Codex 各出一版你来挑 | 推荐，反正只要几十秒 |

## ⚠️ 四个提醒

1. **别让 Codex 自己发挥范围** —— 它很可能给你加上"用户登录""订阅推送""移动端"，这些必须砍掉。提示词里我已经写了"不做清单"，但它有时还是会写，**你拿到后要检查一遍**。
2. **输出后你要做一件事**：把 M1–M4 的功能描述念给李听，问他一句"照这个能写吗"。他要是说"能"，这版 PRD 就定了。
3. **字段名别改** —— 就是数据底表里的 18 列，Codex 要是自创了字段名（比如把「官方编号」写成「法规编号」），**改回来**，否则李开发和张核对会对不上。
4. **v2 新增的两节必须保留** ——「分层保命原则」和「扩展路径」。前者是防止工期崩盘的保险，后者是应对评委问「市场是不是太小了」的答案。

## 📌 范围变更说明（为什么从 1 市场改成 2 市场）

| | v1（旧） | v2（现在） |
|---|---|---|
| 市场 | 仅欧盟 1 个 | **欧盟 + 美国 2 个** |
| 类目 | 3 个 | **5 个 + 通用** |
| 数据 | 待抓取 | **已完成 88 条** |
| 风险控制 | 无 | **分层保命原则** |
| 对外说法 | 无 | **扩展路径（换市场=换接口）** |

**变更理由**：数据线提前完成并超出预期，美国 eCFR 官方接口已跑通，证明「官方接口抓取 → 引用对齐 → 可核验输出」这套方法论是可复制的。用 88 条真实数据 + 双市场做支撑，比 30 条单市场更有说服力；同时用「分层保命」控制工期风险。
