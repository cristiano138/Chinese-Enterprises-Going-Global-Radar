| 链接级 `scripts/check_freshness.py` | 202 空响应被当成“可访问”；`changed` 永远为假；上次运行 10-16；58/86 网络失败 | 修正口径；区分「HTTP 可达」与「确实取到内容」；代理自动降级；重跑并产出可信数据 |
| 字段级 `scripts/check_metadata_freshness.py` | 从未对正式库跑过；输出文件不存在 | 对 2.23GB 正式库跑通；输出改到 `data/`；产出 `law_id` 级变更信号 |
| 定时 | 只有 docstring 示例，没有实际任务 | 提供 Windows 计划任务 + GitHub Actions 两套 19:00/22:00（北京时间）方案 |

## 3. 数据契约（前端只读）

### 3.1 `data/freshness_latest.json`

由 `check_freshness.py` 覆盖写入：

```json
{
  "schema_version": 2,
  "run_id": "20261019T190000+0800-12345",
  "checked_at": "2026-10-19 19:00:12",
  "checked_at_utc": "2026-10-19T11:00:12+00:00",
  "timezone": "Asia/Shanghai",
  "total": 86,
  "http_ok": 57,
  "content_verified": 57,
  "empty_content": 29,
  "ok": 57,
  "failed": 29,
  "link_error": 0,
  "net_error": 0,
  "changed": 0,
  "links": {"<url>": {"...": "..."}}
}
```

口径：

- `http_ok`：HTTP 2xx/3xx，**不等于**拿到了内容。
- `content_verified` / `ok`：HTTP 成功且响应体非空，才计入“已核验”。
- `empty_content`：HTTP 成功但响应体为空（EUR-Lex 当前返回 202 + 空体），**不判死链，也不算已核验**。
- `link_error`：4xx/5xx。
- `net_error`：本机网络未连通，不判死链。
- `changed`：仅当上一次和本次都取得非空哈希且不同。

### 3.2 `data/freshness_log.jsonl` / `data/freshness_runs.jsonl`

- 每链接每次一行（可审计回放）。
- 每次运行汇总一行，供页面展示“最近两次检查”。

### 3.3 `data/metadata_check_latest.json`

由 `check_metadata_freshness.py` 覆盖写入；字段级变更信号：

```json
{
  "schema_version": 2,
  "checked_at": "2026-10-19 19:20:00",
  "timezone": "Asia/Shanghai",
  "total_laws": 86,
  "changed_count": 0,
  "rejected_count": 0,
  "failed_count": 0,
  "failed": [],
  "changes": [{"law_id": "EU:...", "field": "...", "stored": "...", "official": "..."}],
  "upcoming_deadlines": []
}
```

### 3.4 `core/freshness.py`

只读函数，不写文件：

- `load_latest()` / `load_metadata_latest()`
- `read_runs(limit=2)`
- `summarize(now=None, stale_hours=24)`：返回检查时间、距今天数、是否过期、各口径计数、待复核链接、最近两次运行。
- `first_run()`：没有检查记录时返回 `True`，供首页切教程态。

## 4. 定时方案

### 4.1 本地（主方案）

- 入口：`scripts/run_freshness_checks.py`
- 依次执行链接级、字段级检查；写运行日志与汇总。
- Windows 注册：`scripts/install_freshness_schedule.ps1`
  - 任务名：`ComplianceRadar-Freshness`
  - 触发器：每天 19:00、22:00（系统时区 `China Standard Time`，即北京时间）
  - 错过触发时补跑；同一时间只允许一个实例；单步超时 180 分钟，
    任务总时限 300 分钟（86 条字段级检查实测约 60 分钟，留足重试余量）。
- 卸载：同一脚本 `-Uninstall`。

### 4.2 云端（备选）

- `.github/workflows/freshness-check.yml`
- UTC cron：`0 11,14 * * *` = 北京时间 19:00、22:00。
- CI 只跑链接级检查；正式 SQLite 库不在仓库内，字段级检查若无库则记录 `skipped`，不伪造结果。
- 运行结果回写 `data/freshness_latest.json`、日志与运行汇总。

### 4.3 过期判定

- 默认 `stale_hours=24`，可用环境变量 `FRESHNESS_STALE_HOURS` 覆盖。
- 页面应如实显示“最近检查 X 小时前 / 数据可能已过期”，不得伪造。

## 7. 风险与处理

- **代理未开**：当前环境 `HTTP_PROXY=127.0.0.1:7897`，Clash 未运行时连接被拒。脚本默认 `--proxy auto`：先探测代理端口，不可达则自动切直连并记录。
- **EUR-Lex 反爬**：页面返回 202 空体。链接层如实记为 `empty_content`；EU 的权威变更信号由字段层 SPARQL 提供。
- **正式库备份**：`check_metadata_freshness.py` 每次正式运行会复制 2.23GB 库，需预留磁盘；先用 `--dry-run`。
- **GitHub Actions 定时不准**：GitHub cron 可能延迟；本地计划任务是主方案。
- **字段层耗时**：86 条 × 官方接口限速，预计 10–20 分钟；单次任务超时设为 60 分钟。
