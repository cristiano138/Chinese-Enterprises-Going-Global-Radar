# 新法规发现链路（库外法规）

版本：2026-10-19 ｜ 关联：`scripts/discover_new_laws.py`、`core/law_intake.py`、
`scripts/ingest_law_material.py`、`scripts/refresh_recall_pipeline.py`

## 1. 一句话

`scripts/discover_new_laws.py` 去**官方数据源**找 `laws` 表里还没有的法规，
默认只出报告；显式 `--intake` 才建档。发现、去重、编号映射全部由确定性
代码完成，LLM 只做「是否相关 / 品类 / 一句话摘要」。

```text
官方源增量（EUR-Lex SPARQL / Federal Register API）
  -> 与 laws 表比对（CELEX / Title+Part）
  -> LLM 相关性 + 品类（可选）
  -> data/new_law_candidates.json
  -> [--intake] core.law_intake 骨架建档（待人工复核）
  -> [--refresh] 材料待办 + 召回树重建
```

## 2. 数据源与查询口径

### 欧盟：Cellar SPARQL

接口：`https://publications.europa.eu/webapi/rdf/sparql`

按官方发布日期窗口查 sector 3 的 R/L/D 作品：

```sparql
PREFIX cdm: <http://publications.europa.eu/ontology/cdm#>
PREFIX xsd: <http://www.w3.org/2001/XMLSchema#>
SELECT DISTINCT ?celex ?date WHERE {
  ?work cdm:resource_legal_id_celex ?celex .
  ?work cdm:work_date_document ?date .
  FILTER(?date >= "2026-09-01"^^xsd:date && ?date <= "2026-10-19"^^xsd:date)
  FILTER(REGEX(STR(?celex), "^3[0-9]{4}[RLD][0-9]{4}$"))
} ORDER BY DESC(?date) LIMIT 300
```

再用 `VALUES ?celex` 批量补英文 `expression_title` 与 `resource_legal_eli`。
已有 CELEX 的条目不进入候选。

### 美国：Federal Register API

接口：`https://www.federalregister.gov/api/v1/documents.json`

按 CFR Title 逐条查窗口内的最终规则（`conditions[cfr][title]` 不支持数组，
必须一个 Title 一次请求）：

```text
conditions[publication_date][gte]=2026-09-19
conditions[publication_date][lte]=2026-10-19
conditions[type][]=RULE
conditions[cfr][title]=16
order=newest
per_page=100
```

从每条文档的 `cfr_references` 取 `title + part`，与 `laws` 表的
`(title_number, part_number)` 比对。默认 Title 取自 `laws` 表已有值
（当前为 16 / 21 / 47），也可用 `--us-titles` 指定。

## 3. 用法

```bash
# 最近 30 天，两个市场，只出报告
python scripts/discover_new_laws.py

# 指定窗口 / 单市场 / 跳过 LLM
python scripts/discover_new_laws.py --since 2026-09-01 --until 2026-10-19
python scripts/discover_new_laws.py --only EU --no-llm

# 演练建档（不写库、不备份）
python scripts/discover_new_laws.py --intake --intake-limit 5 --dry-run

# 只对 LLM 判定相关的候选建档（默认行为）
python scripts/discover_new_laws.py --intake --intake-limit 5

# 建档后生成材料待办并重建召回树
python scripts/discover_new_laws.py --intake --refresh
```

主要参数：

| 参数 | 默认 | 说明 |
|---|---|---|
| `--since` / `--until` | 今天往前 30 天 / 今天 | 官方发布日期窗口（含端点） |
| `--only` | `EU,US` | 只查指定市场 |
| `--us-titles` | 取 `laws` 表已有 Title | 逗号分隔的 CFR Title |
| `--limit` | 300 | 每个源最多扫描条数 |
| `--no-llm` | 关 | 跳过相关性判断，全部标为不确定 |
| `--intake` | 关 | 调用 `core.law_intake` 建档 |
| `--intake-all` | 关 | 不按 LLM 相关性筛选，建档所有候选 |
| `--intake-limit` | 5 | 单次最多建档条数（美国一条规则含多个新 Part 时按 Part 计） |
| `--refresh` | 关 | 建档后运行 `refresh_recall_pipeline --from-intake-log` |
| `--dry-run` | 关 | 不写报告/日志；`--intake` 也只演练（仍会访问官方接口和 LLM 做预览） |
| `--proxy` | `auto` | `auto` / `direct` / 指定代理 URL |

## 4. 输出

`data/new_law_candidates.json`：

```json
{
  "schema_version": 1,
  "generated_at": "2026-10-19 23:50:00",
  "window": {"since": "2026-09-19", "until": "2026-10-19"},
  "database": {"laws": 86, "eu": 29, "us": 57},
  "sources": [
    {"source": "EU", "ok": true, "scanned": 120,
     "skipped_exists": 0, "candidates": 9, "error": ""}
  ],
  "counts": {"candidates": 9, "llm_relevant": 4, "intaked": 0},
  "candidates": [
    {
      "law_id": "EU:32026R2298",
      "jurisdiction": "EU",
      "celex": "32026R2298",
      "official_title": "Commission Regulation (EU) 2026/2298 ...",
      "published_on": "2026-10-16",
      "eli": "http://data.europa.eu/eli/reg/2026/2298/oj",
      "official_url": "https://eur-lex.europa.eu/legal-content/EN/TXT/?uri=CELEX:32026R2298",
      "first_seen": "2026-10-20 00:10:00",
      "is_new": true,
      "llm": {"ok": true, "relevant": true,
              "category": "食品接触", "summary": "修订食品添加剂使用规定。"}
    }
  ]

```

每次运行还会追加一行汇总到 `data/new_law_discovery_log.jsonl`（不含候选正文）。

`data/new_law_seen.json` 记录每个候选的 `first_seen`（保留 180 天），报告里的
`is_new` / `counts.new` 表示「本轮新出现」——同一个候选在 30 天窗口里被
重复扫描时不会每次都当成新发现。

## 5. 冲突处理（接口优先，管理端留存）

**官方接口是唯一事实来源，搜索/LLM 只是线索。** 当出现：

```text
搜索/LLM：发现一条新法规
官方接口：明确说没有（Cellar 404 / 空内容；FR 404 / 非 Rule）
```

处理规则：

1. **该条不进入** `data/new_law_candidates.json` 的 `candidates`；
2. 写入管理端冲突日志：
   - `data/new_law_conflicts.jsonl`（每次检测追加一行，供审计）
   - `data/new_law_conflicts.json`（按 `identifier + 拒绝原因` 去重的管理端队列，
     带 `first_seen` / `last_seen` / `seen_count`）
3. 冲突记录带 `visibility=admin_only`、`status=pending_review`、
   `priority=admin_review`，并保留搜索来源、查询词、URL、标题、摘要、
   官方接口拒绝原因，供后续管理员系统复核；
4. **普通用户页面只读 `new_law_candidates.json` 的 `candidates`**，
   不得展示任何冲突记录；本轮先留存日志，用户权限分级/管理员系统后续再做。

注意：网络错误、5xx、超时**不算冲突**——那只是“本次没核验”，计入
`sources.WEB.unverified`，下次运行会重试。

## 6. 安全边界

1. **默认不写库**：没有 `--intake` 时只读官方接口 + 写报告。
2. **建档需显式授权**：`--intake` 默认只建档 LLM 判定为相关的候选；
   LLM 不可用时，必须显式 `--intake-all` 才会建档。
3. **整批只备份一次**：`intake_eu_law(..., backup=False)` /
   `intake_us_law(..., backup=False)` 由发现脚本在批次开始前统一备份，
   避免每条法规复制一份 2.2GB 库。
4. **只建骨架**：新法规在 `units` 表没有切片是预期状态；全文落库仍需
   `scripts/ingest_law_material.py` 的 manifest 流程，并保持 `待人工复核`。
5. **LLM 不产生事实**：编号、日期、链接全部来自官方接口；LLM 只输出
   相关性、品类和摘要，异常/超时自动降级为「不确定」。

## 7. 已知限制

- **美国源直连可能 403**：本机实测 Federal Register API 经代理可访问，
  Clash 未启动时直连返回 403。`--proxy auto` 会如实报告该源失败，不会
  伪造空结果；GitHub Actions（美国出口 IP）通常可直连。
- **欧盟窗口是“全部 sector 3 作品”**：包含 CFSP 决定、贸易救济等，需要
  LLM 或人工按相关性过滤；脚本本身不做品类判断。
- **只看官方发布日期**：法规在官方公报发布前不会出现；委员会草案、
  征求意见稿不在本链路内。
- **美国新 Part 有收录时差**：FR 发布新规则后，eCFR 可能还没收录该 Part，
  此时 `law_intake.intake_us_law` 会按“查不到不建档”原则拒绝；候选仍保留在
  报告里，等 eCFR 更新后重跑 `--intake` 即可，不需要人工补编号。
- **发现 ≠ 生效**：候选的 `published_on` 是发布日期，不等于适用日期；
  生效/过渡期以 `check_metadata_freshness.py` 和法规正文为准。
- **不做全文 diff**：发现新法规后仍需人工核对正文与适用范围。

## 8. 建议的定时方式

当前不在 GitHub Actions 里自动建档，建议：

1. 每日/每周跑一次**报告模式**，把 `data/new_law_candidates.json` 作为
   人工复核清单；
2. 复核后本地执行 `--intake --intake-limit N`；
3. 材料齐备后走 `scripts/ingest_law_material.py` + `--refresh`。

如需自动化，可新增一个只跑报告模式、上传 artifact 的 workflow；不要在
CI 中自动 `--intake`（数据库不在仓库里，且新法规需要人工复核）。
