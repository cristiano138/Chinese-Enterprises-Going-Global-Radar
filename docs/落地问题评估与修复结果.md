## 一、评估范围与选取标准

只评估**影响实际上线/真实使用**的问题，按以下三条筛：

1. **有无代码依据**：能指到具体文件或资金/调用路径，不接受「可能有风险」式建议；
2. **是否阻塞上线或使用**：数据错口径、缓存误复用、请求卡死、公网页面无防护优先；
3. **是否可验证**：每条都写出验收标准和已执行/未执行的验证方式。

刻意**排除**的内容：法规扩充、新增国家/市场、多品类矩阵、文件上传与长文解析、账号体系。
这些属于能力扩展，不是当前版本的落地阻塞项，放进│├不切实际也不利于收敛。

## 二、本轮发现并处理的问题（已有代码依据）

### B1｜缓存键只含提示词，换模型/换参数后仍返回旧文本 —— 已修复

- **依据（修复前）**：`core/llm.py:92` `_cache_path()` 仅 `sha256(prompt)[:16]`；`core/llm.py:175` 命中后立即返回。
- **影响**：更换 `MODEL_NAME`、`MODEL_API_BASE`、生成参数后，同一提示词继续返回旧结果，
  表现为「配置改了却像没改」，且后者是完全正确的假象——比直接报错更危险。
- **复现（修复前代码真实回放）**：换模型后 `cached=True`、底层调用仍为 1 次。
- **修复**：`core/llm.py:126` `cache_key()` 纳入提示词、Base、Model、`max_tokens`、`temperature`、
  `thinking` 与格式版本 `CACHE_VERSION`；**不写入 Token**（同见 `config_summary()` 只展示非敏感字段）。
- **预期收益**：配置与结果一致，省下的额度不会以错误结论为代价。
- **验收**：`scripts/selftest_llm_reliability.py`「缓存键隔离」「缓存键不写入 Token」两条通过。

### B2｜缓存目录异常逃出降级逻辑，整个润色回调失败 —— 已修复

- **依据（修复前）**：`core/llm.py:94` `_cache_path()` 内 `os.makedirs()`；`core/llm.py:99` 在自身 `try` 之前调用。
- **影响**：只读挂载、路径被同名文件占用、权限不足时，`PermissionError` 直接外抛，
  上层拿不到「降级结果」，与 README 承诺的「模型失败也能出清单」相矛盾。
- **复现（修复前代码真实回放）**：桩 `makedirs` 抛错后，`chat()` 抛出 `PermissionError`。
- **修复**：`core/llm.py:149` `_cache_get()`、`core/llm.py:171` `_cache_put()` 全路径异常兜底，
  按「未命中」处理；读取时文件损坏同样视为未命中并重算。
- **验收**：同脚本「缓存容错：目录不可建」「缓存容错：文件损坏」两条通过。

### B3｜磁盘缓存无过期、无容量上限 —— 已修复

- **依据（修复前）**：只有写入，没有任何淘汰；`data/cache/` 只增不减，也没有 TTL。
- **影响**：长期运行的服务里缓存无限增长，且提示词或法规口径变化后旧文本永久生效。
- **修复**：`core/llm.py:57-61` 增加 `LLM_CACHE_TTL_SECONDS`（默认 7 天）、
  `LLM_CACHE_MAX_FILES`（默认 512，最旧优先淘汰）、`LLM_CACHE_MAX_BYTES`（单条 200KB 上限）；
  `core/llm.py:178` 原子写（`tmp + os.replace`），避免并发下读到半个文件。
- **验收**：同脚本「缓存治理：过期不复用、容量有上限、单条超限不落盘」通过。

### B4｜M1/M2/M3 润色没有整体超时预算 —— 已修复

- **依据（修复前）**：`core/llm.py:394 / 469 / 519` 三处 `chat(prompt, max_tokens=4000)` 均未传 `timeout`；
  `chat()` 默认 `timeout=None`，即不限总时长。M1.5 路由层（`modules/m15_router.py:310`）有 12 秒保护，但覆盖不到这三处。
- **影响**：一次慢请求会把确定性清单一起拖住；Gradio 同一回调共享并发，会连带影响其他会话。
- **修复**：`core/llm.py:63` 默认总预算 `LLM_TIMEOUT_SECONDS`（默认 45 秒）；
  `core/llm.py:223` 将预算下传到底层 HTTP（`timeout=预算-1s`），并 `max_retries=0`（`core/llm.py:121`），
  避免「外层已放弃、底层还在 SDK 自带重试里慢慢跑」。
- **验收**：同脚本「超时与恢复」通过（预算内降级 + 恢复后新请求成功）。

### B5｜超时后请求仍占线程、新请求无界排队 —— 已修复

- **依据（修复前）**：`ThreadPoolExecutor(max_workers=4)` 的等待队列无界，`fut.cancel()` 无法终止已运行任务。
- **影响**：连续慢请求填满四线程后，后续请求会在队列里排到超时才失败，表现为「整个功能卡住」。
- **修复**：`core/llm.py:257` 在途计数准入，池满即返回带 `busy=True` 的降级结果，不再递交注定排不到的任务；
  计数在 `finally` 释放（`core/llm.py:334`）。
- **验收**：同脚本「并发准入」通过。

## 三、发现但**本轮未改**的问题（避免无效或过度改动）

### C1｜公网部署缺少请求限流与额度保护 —— 未实施

- **依据**：`app_main.py:1300-1305` 绑定 `0.0.0.0` 且未设置 `queue(max_size=...)`；
  未_LIMIT框架默认队列长度上限。
- **影响**：服务可被外部访问时，客户端可连续提交请求消耗模型额度并排挤他人。
- **为什么不顺手改**：真正的限流应在部署层（ModelScope/网关）配置，单靠 `max_size` 只是把队列变短，
  不能防滥用；若改成 `show_api=False` 也只是隐藏文档，不是访问控制——写了会给人错误的安全感。
- **建议动作**：若是演示/内部使用，保持内网或平台鉴权；若要公网，先在部署侧配置并发与速率限制。
- **状态**：**未实施**，也**未验证**部署侧是否已有保护。
