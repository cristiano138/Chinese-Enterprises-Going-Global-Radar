# 部署与上传

本文说明正式项目的安装、提交与发布方法。实际提交和部署结果以当次发布验收记录为准。最终上传源目录固定为：

```text
E:\workbuddy\2026-10-14-01-02-52\compliance-radar
```

`compliance-radar-ui-candidate` 是隔离开发副本。本轮已将确认的代码、资源与文档集成回上述根目录，保留原 `.env`、CSV、快照、质量报告与数据库。以下命令都从原根执行；不要把副本作为第二套正式发布源。

## 1. 本地启动

在 PowerShell 中执行：

```powershell
Set-Location -LiteralPath 'E:\workbuddy\2026-10-14-01-02-52\compliance-radar'
py -3.11 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe app.py
```

已有可用的 Python 3.11 虚拟环境时跳过创建步骤；若没有 `py` 命令，用本机 Python 3.11 的完整路径替换 `py -3.11`。浏览器访问 `http://127.0.0.1:7860`。主入口仍是 `app.py`，由它加载 `app_main.py` 和新的聊天界面；全部路径以项目文件所在位置计算。

本机已安装 `uv`，也可用下面这组已验证的命令创建环境：

```powershell
uv venv --python 3.11 .venv
uv pip install --python .venv\Scripts\python.exe -r requirements.txt
.\.venv\Scripts\python.exe app.py
```

`requirements.txt` 固定 `gradio==6.2.0`。本轮专用验证环境为 Python 3.11.17 / Gradio 6.2.0；请使用项目虚拟环境，避免默认 Python 的其他 Gradio 版本影响结果。

服务监听 `0.0.0.0`；端口依次读取 `PORT`、`SERVER_PORT`，均未设置时为 `7860`。本机端口被占用时可暂时设置 `$env:PORT='7861'`。魔搭空间保留其要求的 `7860`；不要沿用本机临时端口。

## 2. 运行所需文件和可选能力

发布包至少包含这些文件及对应的 Python 包目录：

```text
app.py
app_main.py
ui_chat.py
assets/chat.css
assets/chat.js
requirements.txt
ms_deploy.json
core/
modules/
data/语料核对表_完整版.csv
data/snapshot.json
data/journey_sources.json
```

CSV 是法规查询的数据源，`snapshot.json` 声明快照版本、截止日与审核统计，`journey_sources.json` 是首期对话行动的来源清单。它们必须跟应用版本一起上传。当前根目录的 CSV 和快照已经由 Git 跟踪；原始数据、缓存、用户导出和 SQLite 被忽略。打包脚本直接核验运行文件，不依赖 Git 的跟踪或忽略状态，因此新文件尚未提交时也不会被漏掉。

不配置模型密钥也能通过本地规则和现有语料运行主流程。需要模型理解或润色时，在本机 `.env` 或空间的私密配置中设置 `MODEL_API_TOKEN`、`MODEL_API_BASE`、`MODEL_NAME`，修改后重启。模型名称按实际已开通的服务填写，不要直接照抄模板中的示例型号。`.env.example` 是字段说明，`.env` 和真实密钥不上传。

语音识别是可选能力。默认依赖不安装 `requirements-asr.txt`；语音不可用时仍可输入文字。使用云端转写，需要独立确认服务支持 `/audio/transcriptions`，再配置 `ASR_BACKEND=cloud`、`ASR_API_BASE`、`ASR_API_KEY`、`ASR_MODEL`。文字模型可用不代表语音服务已开通。云端转写会把音频发送至配置的服务。转写后须检查文字，再发送查询。

SQLite 正文库不包含在源码包中。2026-10-19 已从桌面五个分片恢复完整库到根目录 `sqlite/regulations.sqlite3`，备份后应用既有治理补丁。chat1.4 的空间部署另含 `runtime-assets/law-store.bundle` 查询资产，启动时按 `data/law_store_manifest.json` 校验并解压；保留全部现有正文切片和来源，排除抓取日志等非查询内容。详细数据与验收状态见[法规库接入记录](一日收尾与法规库接入-20261019.md)。

维护完整库时仍可配置 `COMPLIANCE_DB_PATH` 为绝对路径；必需表为 `laws/documents/law_documents/units`。显式配置或已有库优先，不被启动资产覆盖。不要把 Windows 本机路径原样填入 Linux 空间，也不要把完整库或抓取日志提交到 GitHub 源码仓库。线上精简库仅用于只读检索，正文同步与治理操作针对完整维护库。

重新生成独立查询资产的方法（拒绝覆盖已有输出）：

```powershell
.\.venv\Scripts\python.exe scripts\build_runtime_law_store.py --db sqlite\regulations.sqlite3 --bundle outputs\law-store-new.bundle --manifest outputs\law-store-new-manifest.json
```

核对输出后，将压缩包作为空间文件 `runtime-assets/law-store.bundle`，将对应清单放到根目录 `data/law_store_manifest.json`，与应用版本一起部署。源码 ZIP 默认不含这份独立资产；只上传源码时须另上传资产，或自行配置完整库，才能使用正文检索。

## 3. 先检查，再生成上传包

```powershell
Set-Location -LiteralPath 'E:\workbuddy\2026-10-14-01-02-52\compliance-radar'
.\.venv\Scripts\python.exe scripts\selftest_all.py
.\.venv\Scripts\python.exe scripts\prepare_release.py --output dist\ComplianceRadar-ui.zip
```

`selftest_all.py` 是现有离线回归入口，会刷新 `data/data_quality_report.json` 的检查报告；它不会在线核验全部法规、调用真实语音服务或证明页面视觉效果。新增对话/界面检查的实际执行记录见 [基线与功能保留](基线与功能保留.md)。

`prepare_release.py` 只生成 ZIP；不提交代码、不联网、不部署。包内第一层直接是 `app.py`，不用再打开一层项目文件夹。它检查入口及其必需的核心模块、运行 CSV、快照、对话来源清单和界面资源，并生成 `RELEASE_MANIFEST.json`，列出各文件的 SHA256。它保留文档中的 XLSX 表格与已命名的正式界面截图，排除诊断截图、虚拟环境、Git 元数据、真实 `.env`、常见密钥文件、缓存、用户导出、SQLite 和大文件分片。它拒绝覆盖已有包；重复生成请换一个输出文件名。

模型历史回答可能含业务文本，`data/m4_replays.jsonl` 默认不入包。当前没有真实回放；以后需要交付回放时，先审查记录可以公开，再在打包命令中追加 `--include-replays`。清单中的 `model_replays_included` 会记录实际是否包含该文件；这个选项不会生成回放。

上传前可直接打开 ZIP，核对文件清单。该脚本按路径与文件名筛选，不代替人工检查曾被写进源码的真实密钥。

## 4. 从根目录上传 GitHub

本轮已从正式根目录提交并推送 GitHub main，实际版本与线上结果见 [线上验收记录](线上验收-20261019.md)。以下候选分支流程供后续改动使用；先确认当前目录和已有远程地址，保留现有 `origin` 配置：

```powershell
Set-Location -LiteralPath 'E:\workbuddy\2026-10-14-01-02-52\compliance-radar'
git status --short
git remote get-url origin
git switch -c ui/chat-candidate-20261019
```

逐项查看 `git status` 和 `git diff`，暂存确认过的修改与新增文件：

```powershell
git add -- app.py app_main.py README.md ui_chat.py assets core data/journey_sources.json scripts docs
git status --short
git diff --cached --stat
git diff --cached --check
```

`core/` 包含新的 `conversation.py` 与 `journey.py`，`scripts/` 包含新增回归脚本和打包脚本，`docs/` 包含新资料覆盖、测试和部署说明，均须随界面提交。请审查暂存内容，确保没有加入与本轮无关的私人文档或浏览器故障截图、下载样本。ZIP 的筛选规则不会替 Git 筛选暂存内容。候选分支名称已存在时使用原分支，或另选名称。

确认暂存内容后：

```powershell
git commit -m 'Improve conversation-first compliance workflow'
git push -u origin ui/chat-candidate-20261019
```

在 GitHub 打开这个候选分支创建 PR，验收后再合并到正式分支。没有 `origin` 时，从目标 GitHub 仓库的 Code 菜单复制实际 HTTPS/SSH 地址，再执行 `git remote add origin`。认证使用 Git 的凭证管理器或已配置的 SSH；不在命令或 remote URL 中拼接 Token。上传方式依据 [GitHub 官方说明](https://docs.github.com/en/get-started/using-git/pushing-commits-to-a-remote-repository)。

## 5. 从同一根目录更新魔搭

2026-10-19 实查的当前发布目标为 [ComplianceRadar-v2](https://modelscope.cn/studios/zhanxy2551/ComplianceRadar-v2)，Git 地址是 `https://www.modelscope.cn/studios/zhanxy2551/ComplianceRadar-v2.git`，目标分支为 `master`。旧说明中的 `ComplianceRadar` 是另一个空间，不要混用。

当前 V2 使用免费 CPU `platform/2v-cpu-8g-mem`、Gradio 6.2.0，部署分支另有本地语音依赖与 LFS 模型。根目录为唯一应用源码；发布时保留目标仓库已有的模型、LFS 配置及平台专用依赖，不能用基础文字依赖覆盖已启用的语音环境。平台实际资源设置与本地配置模板分别核查，不自动升级资源。

chat1.3 的启动入口另检查随空间保留的 Whisper base 权重：若构建器只检出已知的 LFS 指针，则从空间公开文件接口补齐固定版本权重，核对 145217532 字节和 SHA-256 后原子替换。模型完整或未随包提供时不发起下载；未知指针、网络失败和校验失败均不覆盖原文件。首次补齐最多等待约90秒并受单次读取超时限制，失败时保留文字服务并记录无敏感信息的错误类别，语音仍须真实样本验收。

先在目标创空间页面确认空间归属、Git 仓库地址和默认分支。复制页面提供的地址；不要根据空间展示名称猜仓库地址。使用 Gradio SDK，配置与根目录 `ms_deploy.json` 一致：Gradio `6.2.0`、Python `3.11` 基础镜像和 CPU 资源。当前配置不要求 GPU。

魔搭官方提供 Git 同步和空间部署工作流，代码推送与部署状态须分别确认；当前官方指南的默认分支为 `master`，已有空间应以它自己的分支为准。[官方创空间指南](https://modelscope.cn/skills/modelscope/modelscope-studio)、[创建与搭建说明](https://modelscope.cn/docs/studios/create)。

若根目录尚未配置魔搭 remote，在 PowerShell 中输入从页面复制的不含凭证的地址：

```powershell
Set-Location -LiteralPath 'E:\workbuddy\2026-10-14-01-02-52\compliance-radar'
$studioRepoUrl = Read-Host '粘贴魔搭空间 Git 地址（不含 Token）'
git remote add modelscope $studioRepoUrl
git fetch modelscope
git remote show modelscope
```

已有 `modelscope` remote 时跳过添加步骤，先检查它指向的空间。不要为修复地址问题删除已有 remote，也不要使用强制推送。

本次 GitHub main 与魔搭 master 不共享完整历史，不能把 main 直接推到 master。根目录已生成部署分支 `deploy/modelscope-chat11-20261019`，在魔搭原历史上同步已验收源码，并保留平台的语音依赖与 LFS 模型；应用源码提交号记录在部署提交的 `Source-Commit` 中。生成部署提交使用独立 Git 索引，根目录工作区仍在 main，没有从旧部署副本上传。

检查空间的实际分支及差异后，推送本次已生成的部署分支：

```powershell
git log --oneline --left-right deploy/modelscope-chat11-20261019...modelscope/master
git push modelscope deploy/modelscope-chat11-20261019:master
```

如果被拒绝，先获取并处理远程差异；不要使用 `--force`。后续应用改动应基于最新 modelscope/master 生成新的部署提交，同步根目录确认过的源码并保留平台专用文件，而不是重复推送本次旧分支。源仓库为浅克隆时，不把源仓库历史作为额外父提交引入部署历史，避免服务器拒绝 shallow update；源码关联使用提交说明记录。不直接覆盖空间历史。

也可使用目标创空间页面提供的“上传文件”能力，把根目录生成的 ZIP 解压后，将其内部文件及目录按原结构上传。不是把 ZIP 当作 `app.py` 上传。无论选择 Git 还是网页上传，最终空间文件的第一层必须同时能看到 `app.py`、`requirements.txt`、`ms_deploy.json`；`assets/`、`core/`、`modules/`、`data/` 保持目录结构。

在空间私密配置中设置密钥；非敏感的模型地址、模型名、数据库路径按空间配置项设置。配置完成后，使用页面提供的部署/重新部署操作，查看依赖安装日志与运行日志。页面显示运行成功后实际验收：

1. 不填任何密钥时能打开聊天入口，发送“我要把儿童玩具卖到欧盟”。
2. 按追问补充年龄、电气属性与已有准备，确认结果随信息变化，来源可以打开。
3. 更正产品或市场、重置对话，确认旧产品的任务状态没有沿用。
4. 查询时间线、法规、跨市场对比与准备清单，检查待核对项明确标记，下载文件可打开。
5. 在窄屏查看输入和回复；配置语音或数据库后分别验证实际能力，未配置时显示原因。

本地测试通过和 Git 推送成功都不等于魔搭部署已成功；以目标空间的构建结果、运行日志和上述实际使用结果为准。

本次实测普通 deploy 接口曾重复构建旧 sbuild 快照，尽管空间状态显示 Running。遇到这种情况先核查实际版本；使用空间的重新构建操作后，再检查新 sbuild 分支中的版本标记及核心文件是否与部署提交一致。仅重启旧镜像或刷新浏览器不能替代该检查。重建可能耗时数分钟；保持原资源和私密配置，不为排障自动升级资源。

## 6. 保留回退版本

发布前记录已验收的 Git 提交号和目标空间当前版本，保留该版本的完整源码 ZIP。原始开发前快照位于项目同级 `compliance-radar-baseline-20261019.zip`；它不含密钥、数据库和虚拟环境。

仅需本地查看旧版时，把旧 ZIP 解压到新的同级目录，用独立虚拟环境启动在空闲端口，不覆盖当前根目录。需要恢复线上时，从已保留的 Git 提交或源码包准备一个明确的回退提交，检查运行数据与依赖一致，再按上述同一根目录流程上传并重新部署。不要删除当前工作目录、使用强制推送或把旧包直接覆盖原始 CSV、数据库和 `.env`。平台的数据库与私密配置需单独保留，源码回退不会自动恢复它们。
